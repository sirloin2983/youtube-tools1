## 2. 日報で決めること
1. **守る**: YPP の 1,000 万を割りそうか・おすすめの配信で下げられていないか
2. **何を切るか**: どの配信者・どの長さが伸びるか
3. **出し方**: 投稿の時刻・予約の並べ方(参考まで)

項目は「この数字が動いたら何をするか」が言えるものだけ。

## 3. 数える値の定義(正確さのため)
- YPP の基準は**直近 90 日の qualified Shorts views** = 公開中の Shorts の engaged view(冒頭の数秒より先まで見た・ループなし)。非公開・限定公開・削除・広告として見られた分・長尺・画像投稿は数えない(公式: blog.youtube の 2 つの記事。提案の 4 の出典)
- API でいちばん近いのは `engagedViews` を `creatorContentType==SHORTS` で絞った値。API の説明の定義は「最初のフレームより先」で、YPP の定義と同じとは書かれていない → **最初に Studio の数字と並べて差を測り、差を画面に書く**。差があれば安全側(小さいほう)で判定する
- 画面の「視聴回数」(`views`。始まるたびに 1・ループも数える)は判定に使わない。比べる値(engaged ÷ 視聴回数)としてだけ使う
- **遅れ**: データは 48〜72 時間遅れ、あとから直ることがある。日報は「3 日前までの確定」と「直近の見込み」を分けて出し、毎日直近 7 日を取り直して上書きする
- 日付は太平洋時間で区切られる(API の日)。画面は API の日付のまま出し、そう書く

## 4. 日報の中身
### 4-1 要約(折りたたんだとき。3 行)
```
守り   90日 qualified ○○万(余裕 ○%)・30日先の見込み ○○万・崖なし
異変   なし(Shorts フィード経由 ○%・engaged の割合 ○% はいつもの範囲)
昨日   当たり 2 本(#名前・#名前)/ 外れ 1 本
```
- 守りと異変は、何も無ければ灰色の 1 行。危ないとき(下の基準)だけ色と記号で目立たせ、ホームのカードにも出す

### 4-2 本体(開いたとき)の項目
| 記号 | 項目 | 中身 | 動いたら |
| --- | --- | --- | --- |
| A1 | 余裕 | 直近 90 日の qualified の合計と 1,000 万との差・日ごとの推移 | 下回りそうなら本数・中身を見直す |
| A2 | 崖の予定 | 今後 30 日に 90 日の窓から抜ける日のうち、大きい日(窓の日の中央値の 2 倍以上。仮)の日付と減る量 | 崖の前に当たりそうな切り抜きを入れる |
| A3 | 見込み | 30・60 日後の 90 日合計。今ある動画の残りの伸び + 予約済みの本数 × 中央の伸び方。**大当たりは見込まない = 下限** | A1 より先に気づく |
| A4 | 配信の異変 | Shorts フィード経由の割合と engaged ÷ 視聴回数 の 7 日平均が、前の 28 日の範囲から外れた(仮: 20% 以上の低下) | 10-01 の更新(足した価値の無い再投稿を下げる)の疑い → 作り方を見直す |
| B1 | 初速 | 投稿から 1・3・7 日の engaged を、同じ日数の自分の動画の中央値と比べて「当たり(2 倍以上)・外れ(半分以下)」(仮) | 当たりの共通点を探す |
| B2 | 配信者別 | 題名の【#名前】で分けた本数・中央値・平均(大当たり 1 本に引っ張られないよう両方) | 切る配信者の配分 |
| B3 | 長さ別 | 秒数の帯ごとの中央値 | 切る長さ |
| B4 | 登録者 | 1 本あたりの登録者の増加 | 回数は少ないが登録につながる型を見つける |
| C1 | 投稿時刻 | 時刻の帯ごとの初速(中身と混ざるので参考) | 予約の時刻 |

- 危ないときの基準(仮): A1 の余裕が 20% を切る・A3 の下限が 1,000 万を切る・A4 が外れた。基準は使いながら直す
- 「伸び方の形」= 投稿からの日数ごとの engaged の割合の中央値。A3 と B1 が使う。自分の過去分から作る(初回にまとめて取る理由)

## 6. 取り方と置き場所
- **OAuth**: スコープは読むだけの 2 つ `yt-analytics.readonly`(数字)・`youtube.readonly`(自分の動画の一覧・予約の本数・長さ)。PKCE の形で鍵を作る道具を `dev/` に(`dev/dropbox_auth.py` と同じ作り)。refresh token は作業データ `analytics\` に置き、リポジトリに入れない(push_helper の検査にも足す)
  - 同意画面が「テスト」だと refresh token が 7 日で切れる → 「本番」にする。`youtube.readonly` は機密の扱いのスコープなので、審査を受けないと「確認されていないアプリ」の警告が出る(自分だけで使うなら進める)。**実装の最初に確かめる**
- **取る時刻**: 入口が動いていて、前回の成功から 20 時間以上たったとき(起動の少しあと・あとは 1 時間ごとに見る)。手動のボタンはいつでも(連打は止める)。作りの見本は `src/home/backup.py`(スレッド・`run_now`・`snapshot`・状態のファイル)
- **取るもの**: チャンネルの日ごと(Shorts と長尺に分けた views・engagedViews・流入の種類・登録者)と、動画 × 日ごとの engagedViews・views・登録者。初回は全期間、以後は直近 7 日を取り直し + 新しい動画。1 回の取り方(1 本ずつか・まとめて取れるか)と割り当ては実装の最初に確かめる
- **置き場所**: 作業データ `%LOCALAPPDATA%\youtube-tools\analytics\analytics.sqlite`(標準ライブラリの sqlite3)。表は「動画」(ID・題名・投稿日時・長さ・Shorts か・配信者の名前)と「動画 × 日」と「チャンネル × 日」と「取った記録」。数字はリポジトリに入れない(Public の方針)。バックアップは `backup.py` が写す(写す対象に入るか確かめる)
- **重い処理**: 初回のまとめて取る分は `ytt_core/jobs.py` の SLOTS を通す
- **外への通信**: Google の API へ「数字を読む」要求だけ。動画・音声は送らない(方針どおり)
