## 2. 日報で決めること
1. **守る**: YPP の 1,000 万を割りそうか・おすすめの配信で下げられていないか
2. **何を切るか**: どの配信者・どの長さが伸びるか
3. **出し方**: 投稿の時刻・予約の並べ方(参考まで)

項目は「この数字が動いたら何をするか」が言えるものだけ。

## 3. 数える値の定義(正確さのため)
- YPP の基準は**直近 90 日の qualified Shorts views** = 公開中の Shorts の engaged view(冒頭の数秒より先まで見た・ループなし)。非公開・限定公開・削除・広告として見られた分・長尺・画像投稿は数えない(公式: blog.youtube の 2 つの記事。提案の 4 の出典)
- 使う値は Studio のショートのエンゲージビュー(EV。ブックマークの raw の値)。Studio が YPP の判定に使うと説明している値で、API の engagedViews との差の問題は無くなった(10-09)
- 再生回数(始まるたびに 1・ループも数える)は判定に使わない。比べる値(EV ÷ 再生)としてだけ使う。EV と再生回数を文面で混ぜない
- **遅れ**: Studio の数字は指標ごとに遅れ方が違い、あとから増える。確定は指標ごとにデータ自体で決め(12-4 の 3)、確定と速報を分けて出す。データは「スマホでタップした時点」のものをそのまま使い、取り直さない(同じ日に複数あれば最新)
- 日付は太平洋時間の日(Studio の日)。公開時刻は日本時間なので、公開からの日数は 1 か所の関数で数える(12-2 の E2)。画面には日付がどちらの時間かを書く

## 4. 日報の中身
### 4-1 要約(折りたたんだとき。3 行)
```
守り   90日 qualified ○○万(余裕 ○%)・30日先の見込み ○○万・崖なし
異変   なし(Shorts フィード経由 ○%・engaged の割合 ○% はいつもの範囲)
昨日   当たり 2 本(#名前・#名前)/ 外れ 1 本
```

| 週報(月曜) | 何を切るか(週 20〜40 本で比べられる) | B2〜B4・その週の当たりの共通点 | 前の週と並べる |
| 月報(1 日) | 方針 | C1・Shorts と長尺の推移・配信者の配分・**効き目の表(4-4)**・仮の基準の見直し | 前の月と並べる |
- 週報・月報も同じデータの集計(取る仕組みは 1 つ)。出た報告は作業データに残し、あとで読み返せる
- 画面: 5 節のタブに「週報」「月報」を足す(日報・週報・月報・守り・動画・傾向)

### 4-4 効き目の表(月報。「何が効くか」をデータに順位付けさせる)
- ユーザー「いろいろあるが、どのデータが効果的かわからない」(10-09)→ 候補を先に絞らず、**取れる要因を全部並べて、伸びとの関係の強い順に出す**
- 物差し: 投稿から 7 日の engaged(大当たりに引っ張られないよう、比べるのは中央値と順位)
- 要因の候補(追加の手間なしで取れるもの): 配信者・コラボ(【#名前】が複数)・長さ・投稿の時刻と曜日・題名の長さと型(【一言】の言い回し)・元配信から投稿までの時間(説明欄の元配信 URL から)・前の投稿からの間隔・同じ配信者の連投・その日の本数
- 見せ方: 要因ごとに「いちばん伸びる群とそれ以外の差」「本数」「期間の前半と後半で同じ向きか(安定しているか)」。本数が少ない・前後半で向きが変わるものは灰色(当てにならない)
- 交絡(見かけの関係)を減らす: 配信者の影響が大きいので、可能な要因は「同じ配信者の中で比べた差」も出す
- 注意: 関係があっても原因とは限らない(印は「ヒント」)。時刻・題名の型など自分で変えられる要因は、決めた期間だけ交互に変えて試す(試すときは月報に印)のがいちばん確か
- 初回に過去 約 580 本を取るので、実装した日から表が出せる

## 6. 取り方と置き場所(10-09 にブックマーク方式へ書き直し)
- **取り方**: 既存のブックマーク「日次取得」を引き継ぐ(iPhone の Safari で Studio を開いてタップ → Apps Script の doPost → Drive の Youtube日次/raw/<日付>.json)。中身は 12-1(日 × 形式の EV・再生・収益・登録者 / 動画ごとの累計と視聴を継続 % / 公開 92 日以内の動画 × 日)。流入元・CTR・視聴維持の曲線は無い → 4-2 の A4 の「Shorts フィード経由の割合」は取れないので、A4 は EV ÷ 再生と視聴を継続 % の変化で見る
- **受け取り**: Apps Script に「合言葉付きで新しい raw を返す」入口(doGet)を足し、ツールが HTTPS で取りに行く(OAuth なし。Drive のコネクタ・同期アプリも要らない)。合言葉は作業データに置き、リポジトリに入れない(push_helper の検査にも足す)
- **送り返し**: ツールが日報・週報・月報の LINE の文面(と HTML)を Apps Script へ合言葉付きで送り、Apps Script が今の仕組み(out/ → pollAndSend)で LINE へ。LINE の鍵は Google 側のまま
- **いつ**: 入口が動いている間、新しい raw が来ていないかを見る(数分ごと)。来たら分析して送る。送ったあとに同じ日の新しい raw が来たら作り直して送り直す。PC が止まっていた日は、起動したときに追いつく。画面の手動のボタンでもいつでも。作りの見本は `src/home/backup.py`(スレッド・`run_now`・`snapshot`・状態のファイル)
- **置き場所**: 受け取った raw はそのまま作業データ `%LOCALAPPDATA%\youtube-tools\analytics\raw\` に保存(あとで計算をやり直せる)。計算に使う表は `analytics.sqlite`(標準ライブラリの sqlite3)。数字はリポジトリに入れない(Public の方針)。バックアップは `backup.py` が写す(写す対象に入るか確かめる)
- **過去分**: Drive の raw/ にある 9/29〜の分と、raw に入っている日別(チャンネルの最初から)・動画 × 日(公開 92 日以内)を最初に取り込む
- **外への通信**: Apps Script の Web アプリへの受け取りと送り返しだけ。動画・音声は送らない(方針どおり)
- Apps Script を直すのは、受け取り(doGet)と送り返しの入口を足す分だけ。直し方はユーザーに手順で渡す(Apps Script の編集画面はブラウザ)

## 10. API の規約(YouTube API Services Developer Policies。10-09 に原文で確認。**ブックマーク方式に決めたので当てはまらない = 検討の記録**)
自分だけで使うツールでも適用の例外は書かれていない。破ると「割り当ての削減か API の利用停止」(Cloud のプロジェクトの API。チャンネルではない)。
| 決まり | 自分のチャンネル(OAuth で承認 = Authorized Data) | 他のチャンネル(承認なし = Non-Authorized Data) |
| --- | --- | --- |
| 数字の保存 | Analytics・統計は必要なだけ保存してよい。30 日ごとに承認が生きているか確かめる(III.E.4.b) | **統計は 30 日を超えて保存しない**(III.E.4.b)。題名などは 30 日で消すか取り直す(III.E.4.d) |
| まとめる | 自分のチャンネルの中なら可 | **持ち主の違うチャンネルをまとめない**(III.E.2.a)。YouTube の使われ方を知るための利用も不可(III.E.2.b) |

- **決定(10-09 ユーザー)**: いったん「申請する」→ 書式が重いので「送るかは段 5(画面ができて書式の下書きを見てから)で決める」に変更。それまでは計算した値に上の印を付けて作る。送らないと決めたら、計算した値(中央値・倍率・見込み・効き目の表)は API が返す値に寄せるか外す
- 字面では自分のチャンネルの派生の指標(中央値・倍率)にも III.E.4.h がかかる。申請しないで計算を続けると規約違反で、見つかればそのプロジェクトの API が止まる(スタジオの API キーと同じプロジェクトなら、スタジオも止まる)→ すすめない

## 11. 他の切り抜きチャンネル(10-09。**やらない**。検討の記録)
- 10-09 ユーザー「じゃあ他チャンネルはいい」。Data API v3 で代用しても同じ規約(Developer Policies は API サービス全体が対象)。公開ページの自動の読み取りは YouTube の利用規約に触れる
- 取れるもの: Data API の公開の数字だけ(視聴回数・高評価・コメント数・投稿日時・題名・長さ・説明欄)。engaged・維持率・流入は取れない。鍵はスタジオの YouTube の API キーで足りる(OAuth 不要)。新しい動画は投稿の再生リスト経由(安い)で、検索(1 回 100 ユニット)は使わない
- 見たいこと: 他のチャンネルがいま伸ばしている元配信と配信者・切られ尽くした場面・配信から出すまでの時間・当たりの型
- **規約(10 節)の制約**: 統計は 30 日まで・チャンネルをまたいでまとめない・派生の指標を作らない。つまり「配信者別の順位」「他チャンネルの平均との比較」は、10 節の申請が通らない限り作れない
- 申請なしでできる形: チャンネルごとに、直近 30 日の新しい動画を API の数字のまま並べる「見る窓」(まとめ・順位付けなし。30 日より古い数字は消す)
- 公開ページの読み取り(スクレイピング)で規約を避けることはしない

## 12. 既存の「Youtube日次」の監査(10-09。サブエージェント Opus・読むだけ)と作り直しの方針
### 12-1 既存の形
- 日次(Google Drive): Apps Script が raw/<日付>.json(Studio の内部 API の応答)と _daily.json を置き、claude.ai のルーティンが `build_daily.py`(標準ライブラリだけ・LLM なし)を動かして out/ に書き、Apps Script が LINE へ
- 週次・月次(Dropbox の `Youtube分析\_system\`): PC の Chrome で取得 → `weekly_compute.py`・`forecast.py` → LLM が文章 → PDF。**結果は日次の側(Drive の summaries/)へ一度も渡っていない** = 日次は 9/28 に作った見込みと照合を貼り続けた
- raw の中身: 日 × 形式(ショート・長尺・その他・投稿)の EV・再生(ループ込み)・推定収益・登録者 / 動画ごとの累計(EV・再生・**視聴を継続 %**・平均視聴率・収益・登録者。視聴を継続 % は累計だけ)/ 公開 92 日以内の動画 × 日の EV と再生。日別はチャンネルの最初から。**日付は太平洋時間**。流入元・CTR・視聴維持の曲線は無い

### 12-2 誤り・弱点
| # | 何 | 影響 |
| --- | --- | --- |
| E1 | 見込み(届く確率・本数の表・提案)と週次との照合が固定のファイルから。作った日の表示もない | 10 日間同じ確率。同じ時期に週次は別の確率を出し、2 つの違う数字が届いた。照合は同じデータどうしで常に「一致」 |
| E2 | 公開 0 日目のずれ: 日本時間の公開日から数え、日付は太平洋時間 | 日本時間の 0〜16 時台の公開は初日の分が落ちる → 初動の順位・当たり判定・週次の公開 3 日の値が低く出る |
| E3 | 確定日 = 取得時刻の UTC の日付 − 2 日。指標ごとの遅れ(EV と収益で違う)を区別しない | 確定日が取得時刻で 1 日ずれる・まだ 0 の値を「確定」扱い |
| E4 | 「週」の定義が 3 通り(レポート日の前 7 日・確定日までの 7 日・28 日 ÷ 4)。非公開・予約の扱いなし | 本数が場所ごとに違う(「16 本」の一因) |
| E5 | 見込みの確率は直近 4 週の水準の仮定でほぼ決まり、答え合わせが無い。食い合いが仮の値になることがある。期限の前提(1/31)の出どころの記録なし | 1 週で大きく動く・当てにしてよいか分からない |
| E6 | 「順調」の信号と低い確率が同じ文面に並ぶ。見込みのばらつきを出さない。「今日やること」は数本のハッシュタグが根拠でほぼ毎日同じ。視聴を継続 % の境目が日次と週次で違う | 矛盾した指示・同じ提案の繰り返し |
| E7 | 週次・月次の文章は LLM が毎回書き、数字は手で合わせる。検査なし | 版ごとに数字が変わる |

### 12-3 引き継ぐ良い点
- 取り方(ブックマーク → Studio の内部 API。API では取れない視聴を継続 % まで 1 回で)
- 日次は決まった型・LLM なし・冪等(out にあれば何もしない)・html → json の順に置いて通知が先走らない・催促と失敗の知らせ
- 確定と速報を分けて見せる(斜線)・初動を「同じ日数の時点での過去の順位」と四分位の帯で見る
- 視聴を継続 % は当たりとの関係が強い(毎日の注目の指標に残す。ただし「冒頭を変えれば上がる」は未検証)
- 週次の提案に成功の基準と判定日を付け、翌週に判定する輪。予測の作り(食い合い 3 通り・乱数の種を固定・古い動画の減りを足す)
- 書き方の決まり(EV と再生回数を混ぜない・用語の欄)・スマホ幅のページ

### 12-4 作り直しの方針
1. **1 つの計算部品**: 日報・週報・月報・画面はすべて同じ部品(src/analytics/)が同じ raw から作る。固定のファイルに頼らない(E1・E7)
2. **時刻と日付を 1 か所で定義**: 太平洋時間の日・日本時間の公開時刻・公開からの日数の数え方・「週」(月曜〜日曜の確定した週と、直近 7 日を名前で区別)を 1 か所に(E2・E3・E4)
3. **指標ごとの確定**: 確定日は指標ごとに、データ自体(前回の取得からの変化)で決める(E3)
4. **すべての数字に出どころ**: 「何時何分にタップしたデータ」「何日までの確定」「計算した日」を数字の横に。見込みは作った日と前提を必ず書く(E1・E5)
5. **答え合わせ**: 見込みは過去の時点から出し直して実際と比べた当たり具合を毎回出す。当たらない見込みは出さない・幅を出す(E5)
6. **食い違いの検査**: 本数・合計など同じ値を別の道で数えて、合わなければ文面に警告(E4・E7)。信号と確率が矛盾したら、どちらが何を見ているかを書く(E6)
7. **提案は根拠の強さ付き**: 本数・期間の前後半で同じ向きか(4-4 の効き目の表と同じ考え)。弱い提案は出さないか「ヒント」と書く。同じ提案が続くなら理由を書くか外す(E6)
8. **LLM は数字を作らない**: 文章を LLM に書かせる場合も、数字は部品が出した値を差し込むだけ(E7)
9. 期限(1/31 か・2/1 以降は常に 90 日の窓か)は公式の文言で確かめて書く(E5)
