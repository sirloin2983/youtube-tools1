## 2. 詳細

### A. 投稿の後(閉ループ: 投稿 → 伸び → 検出と構成に戻す)

#### P1 投稿の記録と伸びの取り込み
- 何を: 投稿済みの動画 ID を案件(切り抜き)に紐づけ、毎日 Analytics API で 再生・エンゲージビュー・維持率の曲線・流入の種類・高評価・コメント数を取り、作業データに貯める(JSONL か SQLite)。ホームの案件に「伸び」の列と、配信者別の集計
- なぜ: 今の線 C の入口は「採用の記録 配信 10 本」(今 0)。本当の正解は「視聴者が見たか」で、**投稿済み 約 580 本の実績が既にある**。10 本待ちより先に学習の材料が手に入る
- どう作る: OAuth(`yt-analytics.readonly`。同意画面を本番公開にして 7 日切れを避ける)・紐づけは説明欄の元配信 URL(`?t=` があれば区間も)と題名から自動(過去分も一度に)・1 本 1 クエリ(580 本でも割り当ての中)。音声・動画は送らない(数字を読むだけ)
- 大きさ M。ユーザー: Cloud Console で OAuth を作る 20 分
- リスク: 低(読むだけ)。データは 48〜72 時間遅れ
- 議論: 過去の 580 本は切り抜きの区間が残っていない(`?t=` のある分だけ)。これからの分は案件に自動で残す

#### P2 「視聴を継続 %」と維持率の曲線を Chrome 拡張で控える
- 何を: `chrome-ext/yt-studio-time` は Studio の内部 API の応答を既に読んでいる(`world: MAIN`)。同じ仕組みで、1 本ごとの画面を開いたときの「視聴を継続 %」と曲線を控え、入口(localhost:8700)の API に送る(または JSON をダウンロード)
- なぜ: フック(冒頭 3 秒)の良し悪しを測る唯一の指標で、API では取れない。P10 の効果はこれでしか測れない
- 大きさ S〜M。リスク: Studio の内部 API の形が変わると壊れる(拡張の前提と同じ)。入口へ送るには拡張に `host_permissions`(localhost だけ)が要る = 「権限なし」の方針の変更
- 議論: 権限を足してよいか。ダウンロードで済ませるなら権限なしのまま

#### P3 投稿の下書き(段 13 の再提案 + 非公開でアップロード)
- 何を: 案件に「投稿」の欄。Resolve で書き出した mp4 を登録 → 題名案(【一言】の候補 + 本文)・説明欄(規定どおり**冒頭に元 URL と題名**、`?t=` 付き)・ハッシュタグ(配信者のタグは名簿から)を型で作る → Data API で**非公開**で上げる(審査なしでできる)→ Studio で目視して公開か予約(今の手順のまま)
- 一言と本文の候補はローカル LLM(llama.cpp Vulkan。Qwen3 8B 程度)に校正済み字幕と話者を渡して 5 案。LLM なしの型だけでも 8 割はできる(名前・タグ・元 URL は決まっている)
- 大きさ M。ユーザー: OAuth(upload)の設定 20 分 + 1 本の試し
- 以前の却下(10-01)から変わった点: ローカル LLM・API の費用が 1 本 100 ユニット・審査なしで非公開まで行ける・10-01 の更新で「独自のコメント」の価値が上がった
- リスク: 非公開固定の動画を Studio で公開に変えられるかは未確認(1 本試せば分かる)。説明欄の一括生成が「量産」に見えないよう、一言は人が選ぶ
- 議論: 投稿の前の目視は残す(全自動にしない)でよいか。段 13 を「やらない」に戻すなら理由を記録したい

#### P28 Qwen3-ASR の context に名簿と配信の題名を渡して測る(最初に。安い)
- 何を: 導入済みの Qwen3-ASR 1.7B(GPU)は、学習に context biasing のデータを含み、システムプロンプトで語彙・人名を渡せる(モデルカード)。名簿(漢字 + かな)・配信の題名・直前の行 を渡して、22 本の評価セットで CER と名前の再現率を測る(`dev/eval_asr.py`・`eval_alt.py` の流れ)

- 大きさ S。リスク: 日本語の固有名詞での効果の公開データが無い(測るだけ)。効けば「別」の候補(D1-b)の質が上がる

#### P27 新しい日本語 ASR 2 つを評価セットで測る
- 何を: transcribe.cpp(handy-computer。MIT。ggml。`-DTRANSCRIBE_VULKAN=ON` で Windows の Vulkan)で Fun-ASR-MLT-Nano-2512(800M・hotwords 対応)と Cohere Transcribe 03-2026(2B・Apache-2.0)を動かし、22 本で CER を測る。時刻は付かないので Qwen3-ForcedAligner-0.6B か whisper の行の時刻を流用
- なぜ: 読み上げ音声(FLEURS 日本語)の CER は Fun-ASR-MLT 2.3 / whisper large-v3 4.8 / Qwen3-ASR 1.7B 5.3 / SenseVoice 7.6(第三者の集計。確度 中)。配信の音(BGM・重なり)では別物なので、自前の評価セットで測る価値がある。SenseVoice は既に後処理 A で使っていて、同じ系統の新版という位置づけ
- 大きさ S〜M(ビルドが要る。VS Build Tools と Vulkan SDK は入っている)。リスク: Fun-ASR のライセンス表記が HF(Apache-2.0)と配布元で食い違う(確認してから)。10-04 の決定「別モデル 9 種は効かなかった」と重なるが、この 2 つは 2025-12 以降の新顔

#### P18 LLM の後処理(「LLM での書き直し」の再提案。疑わしい箇所だけ・守り 4 つつき)
- 研究で分かっていること(日本語): 微調整した 7B + n-best で Whisper large-v3 の CER 12.9% → 7.8%(100 発話の小さなベンチ)。固有名詞の再現率 44.5% → 82%(LLM をレアワードで微調整した場合)。**プロンプトだけ・n-best だけではほぼ効かない**(15.5 → 15.4)。選別なしに全行を直させると発話の 43% を書き換える過剰訂正になり、選別すると書き換え率 11〜14% で相対 1〜4% の改善。速度は RX 7800 XT の Vulkan で 7B Q4 が約 118 トークン/秒(14B は 40〜50 の推定)= 1 時間分でも数分
- 何を: 全行ではなく**疑わしい箇所だけ**(2 つの認識の不一致・信頼度の低い語・名簿に近い音の語)を、前後 2 行 + 名簿の候補 + 配信の題名 と一緒に 7〜14B(Q4_K_M)へ渡し、置換案を**差分の JSON** だけで出させる。制限: 変えてよいのは聞き違い・助詞・固有名詞、文字数の差 ±20%、名簿に無い名前は作らない、1 文書の編集率に上限。変えた行に印・元の値を残して 1 クリックで戻せる・既定オンのスイッチ 1 つ・評価用には当てない・生の結果を残す(10-08 の方針)
- なぜ: 10-08 に効いたのは「名簿の表記ゆれ直し」= 固有名詞の後処理。LLM はその一般化で、全体の CER より**固有名詞の再現率**(今 47.5%)に効く見込み
- 大きさ M。測り方: 22 本で CER と名前の再現率(K1 と同じ道具)。P28 で Qwen3-ASR の context が効くなら、そちらが先(LLM より安い)
- リスク: 幻覚(勝手な書き換え)。上の制限と印で抑える。議論: 「LLM での書き直し」の却下の理由(記録なし)。守り付きなら試してよいか

#### 補足: ローカル AI の調査で分かった「やらなくてよいこと」
- ノイズ除去(DeepFilterNet3・RNNoise)は Whisper の精度を上げない(RNNoise は悪化の報告)。10-08 の「音声フィルタ 3 種は効かない」と一致 → 再提案しない
- 重なり声の分離(MossFormer2・TF-GridNet)は分離の指標が上がっても ASR の誤りが下がるとは限らない。英語中心で日本語の比較が無い → 線 B の「正解 30 区間がたまってから」のまま。先にやるなら「重なり区間の検出 → 校正の順番付け(人が先に見る)」のほうが安い
- 話者の声紋は区間を長く取り、重なりのフレームを除いて平均すると照合(今 80%)が上がる見込み(推定)。pyannote community-1(CPU)との比較は improvements の既存項目(10 本たまってから)のまま

#### P19 ショート向けの「軽い校正」
- 今: 校正は全行を直す前提(校正の進み具合も全行で数える)。ユーザー「ショートの字幕は会話の全部ではなく、聞こえるままでもない」(10-04)
- 提案: 編集に「字幕に出さない」の一括(無音・相槌・短い行・ゲーム音声)と、進み具合を「出す行」だけで数える。ショート(60 秒以内)の文書は既定で「出す行だけ校正」のモード
- 大きさ S〜M。議論: 今ショートの字幕は全部出しているか・出さない行をどう決めているか
