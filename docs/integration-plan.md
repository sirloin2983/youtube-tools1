# ツールの統合計画(2026-09-24 作成・2026-09-25 更新)

3つのツール(切り抜きスタジオ・文字起こしツール・cut2resolve)を、1つのアプリとして使えるようにするための計画。
本文(議論・比較の全文)は claude.ai の Claude Docs「動画編集ツール 統合計画」(**正本**)。ここは実装する AI が読むための要約。
食い違ったら Claude Docs が正。claude.ai の Project の `claude/*.md` と `docs/project/` は写しで、古いことがある。

## 決まっていること
- **作り直しはしない**。今の構成(Python 標準ライブラリ中心のサーバー + 画面)のまま、新しい入れ物が既存のツールを1つずつ取り込む
- **段階3 の統合対象は、スタジオ・文字起こし・cut2resolve の3つ**(ユーザー判断 2026-09-25。09-24 の「cut2resolve 以外を先に」から拡大)。
  理由: 09-25 に cut2resolve v0.4.0 の Text+ パックが Resolve 実機で成功した(60fps 横の動画 → 30fps のタイムラインで字幕の位置一致を確認)。
  以前の除外理由(Resolve 実機未確認・形が決まっていない)は解消した。**友人の PC での実機確認も済んだ**(09-25 ユーザー確認)
- Resolve への渡し方は **Text+ パックが本命**。EDL は Text+ の予備として残し、EDL 取り込みの実機確認は当面しない(ユーザー判断 09-25)
- **ゲート条件(段階3 に入る前に必ず)**: cut2resolve の未コミットの変更(0.3.2 → 0.4.0、11ファイル)にテストを足して実行し、コミットする。
  対象: `resolve_textplus.py`・`pack.py`・`cut2resolve.py`・`serve.py`・`cut2resolve_core.py`・`app.js`・`index.html`・`README.txt`・`test_pack.py`・`test_serve.py`・`resolve_lua_mock.lua`(新規・未追跡)。
  `git status` で cut2resolve/ に未コミットが無いことを確かめてから段階3 を始める。
  テストは 09-25 に済(test_pack 53・test_cut2resolve 119(Text+ の CLI 経路 2件を追加)・test_serve 23・e2e_ui・ytt_core・app・tools/e2e_pipeline すべて OK)。**残りはコミットだけ**
- 取り込みの順(決定 09-25): **スタジオ → cut2resolve → 文字起こし**。
  cut2resolve は小さく(serve.py 約980行)、重い処理は ffmpeg の別プロセスなので1プロセスに入れても安全で、担当も Claude。
  文字起こしは最大規模(serve.py 約3,800行)で、認識を別プロセスのワーカーに分ける作業が要り、精度改善も並行して進んでいるので最後
- 取り込み方式(決定 09-25): **ファイルを動かさずに取り込む**(`git mv` によるパッケージ化はしない)。
  統合サーバーが各ツールの `serve.py` を別の名前(例 `studio_serve`)で読み込み、ツールのフォルダを `sys.path` に足して、ツールの中の import(`import common` など)はそのまま使う。
  理由: Claude(Cowork)は PC でファイルの移動・改名・git を実行できない。移動しなければ旧起動方法(各ツールの start.bat・`serve.py`)もそのまま動き、git mv による他の AI との競合も起きない。
  守ること: ツール間で**同じ名前の Python モジュールを作らない**(09-25 時点で重なるのは `serve.py` と画面テストの `e2e_ui.py` だけ)。これをテストで検査する。
  各ツールの `serve.py` は、import しただけでサーバーやスレッドが動かない形にする(起動は `main()` の中だけ)
- cut2resolve を取り込むまでの間は、今のまま別アプリ(:8810)で、URL のリンク + ファイル(transcript/v1・cut-plan/v1・SRT)で連携する。`.runtime/` と `/api/siblings` もそれまで残す
- Resolve パックの二重実装(文字起こしの `resolve_export.py` と cut2resolve の `pack.py`)は段階3 で一本化する。**先に契約テスト**(同じ入力から同じパックの中身ができること)を書いてから寄せる(下の「リスク」)
- **個別ツールの完成の基準**(決定 09-25): 主要機能が動けば、段階3 に入り、統合しながら並行で仕上げる(完成を待たない)
- **統合作業の担当**(決定 09-25): Claude が主担当。担当中のツール・ファイルは、他の AI が触らない(`AGENTS.md` の「担当表」)
- **作業データの置き場**(決定 09-25): リポジトリの外(PC 上の別フォルダ)。段階4 の案件データ・移行先もここ。具体的な場所は段階4 の着手時に決める
- **旧ツールの起動方法**(決定 09-25): 統合後も残す(移行期間の保険)。各ツールの start.bat・`serve.py [ポート]` と入口(`start-all.bat`)は消さない
- **画面の表示**(ブラウザのまま / pywebview): 段階3 の実装後に検討(保留)。それまではブラウザのまま
- 段階0〜2 はツールの開発と並行してよい

## 案の比較(要点)
| 案 | 中身 | 判断 |
|---|---|---|
| A. 起動役 + 入口の画面 | 3つのサーバーをまとめて起動・終了、入口から各ツールへ | 段階1として実装済み(`app/`) |
| B. 中継サーバー(1ポート) | 1つのポートで受けて各サーバーへ流す | 見送り(動画の Range・長い通信の中継が不具合の種。C で捨てるコード) |

| D. 作り直し(FastAPI・React・Electron など) | 一から | 不採用(約100件の修正とテストを捨てる・依存が増える) |

## 段階1(入口)の約束 — 各ツールを変えるときに守ること
入口(`app/launch.py`)は各ツールの次の約束に依存している。変えるときは `app/launch.py` と `app/test_launch.py` も直す。
- 起動: 各ツールのフォルダで `serve.py <開始ポート> --no-open`(使用中なら次の番号。同じツールが動いていれば「すでに起動しています」で 0 終了)
- 準備完了: `.runtime/<ツールID>.json`(`{"tool", "port", ...}`)を書き、`GET /api/ping` が `{"app": ...}` を返す(`docs/pipeline.md` の 4)
- 停止: SIGTERM(Windows は Ctrl+Break = SIGBREAK)で `.runtime` を消して終わる。入口は8秒待って終わらなければ強制終了する
- 版: スタジオ・文字起こしは `serve.py` の `SERVER_VERSION = "..."`、cut2resolve は `cut2resolve_core.py` の `VERSION = "..."` を読む(別の画面で古い版が動いているときの表示用)
- 入口のポートは 8700〜8719。ツールの範囲(文字起こし 8775〜8794・スタジオ 8800〜・cut2resolve 8810〜)と重ねない

## 段階2で決めたこと(ytt_core)
- 置き場所はリポジトリ直下の `ytt_core/`(標準ライブラリだけ)。各ツールは起動時に「環境変数 `YTT_CORE_DIR` → 自分のフォルダの1つ上」の順に探して
  `sys.path` の**末尾**に足す(ツールの同名モジュールを隠さないため)。見つからなければ理由を出して起動しない
- ツールを一時フォルダに写して動かすテスト(文字起こしの e2e・test_backend・test_metrics、tools/e2e_pipeline.py・baseline_analysis.py)は
  `YTT_CORE_DIR` をリポジトリ直下にする1行を足した
- 既存の関数名(スタジオ `common.atomic_write`・`handoff.*`、文字起こし `atomic_write`・`pipeline_io.*`)は残し、中身だけ ytt_core を呼ぶ(呼び出し側とテストを変えないため)
- 動きの違いを1つにそろえたもの: 置き換えのやり直しは「Windows の winerror 5・32・33 のときだけ、4回(待ち合計 0.7 秒)」に統一
  (文字起こしは以前「Windows の PermissionError なら6回」。待ちの合計はほぼ同じ)。`.runtime` のポートは 1024〜65535 に統一(文字起こしは以前 1〜)
- fsync: 文字起こしは「失敗したら保存も失敗」(校正の成果を守る)、スタジオは「できなくても続ける」をそのまま残した(`fsync_required`)
- 段階2に入れなかったもの: ffmpeg / ffprobe の呼び出し(スタジオは ffprobe の JSON、文字起こしは ffmpeg -i の出力を読むなど、やり方が違う)と
  ジョブの型(待機列・取り消し・進み具合の持ち方がツールごとに違う)。段階3で1つのサーバーにするときに、ジョブ管理と一緒に作る
- 段階2 の時点では cut2resolve は ytt_core を使わない(当時は統合の対象外だったため)。ツールID と app の対応がずれていないことだけ `ytt_core/test_ytt_core.py` が確かめる。
  09-25 に段階3 の対象へ入ったので、ytt_core への切り替えは段階3 で取り込むときに行う

## 段階3-1(スタジオの取り込み)で決めたこと — 次の取り込みでも同じ形にする
- 置き場所: 入口と同じアドレスの `/studio/`(ユーザー判断 09-25)。入口のサーバー(`app/launch.py`)が要求の最初の行を覗いて、`/studio` で始まれば
  スタジオの Handler(`app/mount.py` が包んだもの)に、それ以外は入口の Handler に渡す。1つの接続に1つの要求(HTTP/1.0 のまま)
- 読み込み: `app/mount.py` がスタジオの serve.py を `ytt_tool_studio` という名前で読み込み、`prepare(port, "/studio/")` を呼ぶ(待ち受け以外の起動の準備。
  スタジオの main() も同じ関数を使う)。終了時は `finish()`(.runtime を消す)。取り込めなければ自動で別のプログラムとして起動する。`--no-mount` で以前の動き
- ツールの画面は**相対パス**で部品を読み、API・メディアの URL は1か所の関数で作る(スタジオは `Studio.base` を画面の場所から決める)。絶対パス `/xxx` を書かない
- `.runtime/<ID>.json` に `"path": "/studio/"` を書く。`/api/siblings` は `"paths": {"studio": "/studio/"}` を付け(無ければ付けない)、ui-kit の `UIKit.tools.setPaths()` がリンクに使う。
  問い合わせは `<path>api/ping`(同じポートでも場所が違えば別のツール)。cut2resolve の siblings も同じ規則に合わせた
- 同じアドレスになる分の安全対策: 取り込んだ画面に CSP(`script-src 'self'` + YouTube のプレイヤーだけ。インラインのスクリプト・`onclick=` は動かない)、
  書き込み系(GET・HEAD 以外)の要求に合言葉(CSRF トークン。起動ごとに作り、画面に `<meta name="ytt-token">` で渡す。ヘッダー `X-YTT-Token`)。入口の API も同じ合言葉。
  Host・Origin・Sec-Fetch の検査はツールの Handler がそのまま行う(許可するホストは入口のポート)
- 二重起動の防止: 入口の中で動いている間に start.bat でスタジオを起動すると、2つ目は立てずに入口の中のスタジオを開く(同じ data.json を取り合わないため)
- ツール間で同じ名前の部品(.py)を作らない。`app/test_mount.py` が clip-studio・cut2resolve・transcribe-tool・app・ytt_core を調べる。実行時にも重なれば取り込まない
- データの置き場所はまだ各ツールのフォルダのまま(リポジトリの外へ移すのは段階4)
- 取り込んだツールは入口と一緒に動くので、入口の画面の「停止」「再起動」は押せない(「すべて終了」で一緒に終わる)

## 主なリスクと対策
優先度の高いものと、AI が作業するときの守り方は `AGENTS.md` の「統合作業のリスク」にもある(実装する AI はそちらを必ず読む)。
- 【高】複数の AI の同時編集: ツール単位の担当表(担当中は他の AI が触らない)、ファイル移動は `git mv` を1コミットにまとめ前後で WORKLOG に告知、長く分かれたブランチは使わない(同じフォルダを2つの AI が使うため)
- 【高】同一オリジン化(段階3)で、1つの画面の XSS が全ツールの API(ファイルの書き込み・Resolve へのスクリプト登録)に届く: CSP `script-src 'self'` の維持、インラインスクリプトの外部化、書き込み系 POST に CSRF トークン、Host/Origin 検査の共通化、パスは許可フォルダだけ
- 【高】1プロセス化での障害の波及: 文字起こし(faster-whisper)は別プロセスのワーカーに分け、落ちたら再起動。同じプロセスに読み込まない
- 【高】Resolve パックの二重実装(`resolve_export.py` と `pack.py`)の一本化: 先に契約テストを書き、それが緑のまま寄せる
- 【高】文書の食い違い: `claude/*.md`(Project)と `docs/project/` は写しで古いことがある。正本は claude.ai の Claude Docs
- CPU の取り合い: ジョブ管理で同時実行数を制限(例: 文字起こし 1、ffmpeg 2)
- データ移行: コピーのみ、元のフォルダは一定期間残す、削除はユーザー確認後
- Public リポジトリへの個人データ混入: 作業データはリポジトリの外に置き、コミット前の検査を足す
