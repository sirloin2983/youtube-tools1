# 文字起こしツール v0.7.0(開発メモ)

切り抜きマーカー(v1.0.0)とは別の独立ツール。ローカルWebアプリ(serve.py + index.html)、標準ポート8775。serve.py の SERVER_VERSION と index.html の APP_VERSION は必ず両方上げる(不一致だと赤い帯が出る。「変わってない」報告の原因になった)。

## 利用環境
- 友人: NVIDIA RTX 3060(CUDA で GPU 利用可)。ただし学習・開発用には使えない(本人談)
- 本人: AMD Radeon RX 7800 XT(faster-whisper は AMD GPU 非対応 → CPU 処理)
- 手元に正解データ(人が聞き取った文章)は無い。使いながら学習させたい方針。**最終的な品質が最優先で、学習段階のコスト(クラウドGPUなど)はかけてよい**(v0.7.0 時点の本人談)

## 決めたこと
- エンジン: ローカルの faster-whisper。処理方式は 自動 / GPU / CPU から選択(自動: GPU が使えれば GPU、失敗したら CPU)
- GPU: NVIDIA のみ。install-gpu.bat で cuBLAS(CUDA12)/cuDNN(9) を pip 導入し、起動時に DLL の場所を登録
- 入力: 手元の動画・音声ファイル(範囲指定可) / 切り抜きマーカーのポイント範囲
- 出力: SRT / VTT / テキスト / JSON。折り返し文字数、話者名付き、範囲の開始を0秒にする
- 編集: 行の修正、分割・結合・削除、時刻入力、検索、要確認フィルタ(文字/話者/提案あり)、一括置換+置換辞書、元に戻す、自動保存

## 精度対策(v0.2.1)
- モデル: large-v3-turbo を追加。kotoba-whisper は chunk_length=15
- 声の検出(VAD): 既定「弱め」。音量補正(highpass+dynaudnorm)、用語集(initial_prompt + hotwords)
- ユーザー報告: 「だいぶ改善した」
- 現状(コード確認済み): condition_on_previous_text=False、beam 5(速度優先で1)、要確認フラグ(make_flags: avg_logprob<-1.0 / no_speech_prob>0.6 / compression_ratio>2.4 / 定型の幻覚文 / 同じ文の繰り返し)は実装済み

## 話者の自動判別(v0.3.0 → v0.4.0)
- sherpa-onnx(CPU、PyTorch 不要)。任意導入(install-diarize.bat / .command)。区間検出は pyannote segmentation 3.0
- 声の特徴モデルは選択式: voxceleb(既定)/ campplus / standard。固定URL + SHA-256 検証、初回に自動DL
- 各行に最大重なりの話者を割り当て。要確認: 声が混ざっている可能性 / 話者が不確か / 話者を判別できなかった
- ユーザー評価: VoxCeleb ResNet34 と CAM++ は「そこそこの精度」、人数指定で精度上昇、要確認が多いのは文字起こし自体の失敗が原因
- 操作: Alt+1〜9 で行の話者切替、「▶ 聞く」、人数・モデルの選択を保存

## 文字の修正・学習(v0.5.0 / v0.5.1)
- 元の認識結果: 文字起こしファイルに `original`(機械の出力 [{start,end,text}])を保存。segments(編集後)とは別。PUT では変更されない
- 置換辞書の自動適用: 文字起こし完了時に settings.json の replacements を適用(既定オン。`autoDict`)。original には適用前の文字を残す
- 修正から学習: original と編集後を、時刻が重なるまとまりごとに突き合わせ(分割・結合に対応)、difflib で置換(誤, 正)を抽出。句読点のみ・12文字超・行の追加削除は除外。1文字の違いは前後1文字を足す(ctx。用語集には入れない)。GET /api/learned?min=N。辞書登録済み・無視済み(settings.learnIgnore)は除外。**候補の辞書登録は必ず人が行う**(誤爆防止)
- v0.5.1: 候補欄の「誤」「正」をその場で編集して登録できる(同じ誤の既存行は置換、編集した場合は元候補を自動で無視、下書きは更新しても残る)
- 再認識: POST /api/retranscribe {tid, ids, model, ...}。対象行の音声(前後0.3秒)だけを、指定モデルで認識(VAD なし・beam 5・用語集)。テキストとフラグ(話者の印は残す)を更新、original も新しい機械出力に差し替える(再認識を「人の修正」と誤学習しない)。直前状態を .bak に1世代保存。判別と同じ待機列・同じ編集ロック
- セキュリティ修正: MODEL_RE が「../x」を通していたのを修正(先頭が . の名前は拒否)
- 制約: v0.5 以前の文字起こしは original が無く学習できない

## 「参考にする」学習(v0.6.0)
置換辞書(無条件の全置換。同音異義語で誤爆しうる)を補う方針。辞書は「必ず直したい固有名詞」用に残し、文脈しだいのものは提案で扱う。
- **A. 修正の提案**: `learn_events` が (誤, 正, ctx, 直前2文字, 直後2文字) を取り出す。`learn_rules` が全文字起こしから 直した回数(pos)・文書数・前後の文字と、「そのまま残した例」(neg: 1か所以上直した=見直した文字起こしの最終テキストに残る誤の文字列。正の中に含まれる箇所は除外)を集計(更新日時でキャッシュ)。確度 `_tier`: 高=pos≥3・2件以上・negなし・却下なし / 中=(直前直後1文字が一致する例で数えた)直した例 ÷ (直した例+そのまま例+却下×2) ≥ 0.6 / それ以外は出さない。定数 HIGH_POS, HIGH_DOCS, MID_RATIO, REJECT_WEIGHT は実データで調整する前提の初期値(推測)
- API: GET /api/suggest?id= → 各行の提案 [{seg,i,wrong,right,tier,pos,neg}]。POST /api/suggest/feedback {tid,action:accept|reject,items}。記録は learn-feedback.json(settings.json と別。画面側の設定保存と競合させないため)。reject は行ごとの dismissed にも記録
- 画面: 各行に「候補 誤→正 [採用][却下]」(確度高は二重線の枠)。採用はテキスト置換+元に戻す対応、却下はその行に出なくなり、置換全体の確度も下げる。「確度高の提案を全部採用」ボタン。要確認欄に「修正の提案がある行だけ」
- **自動置換(既定オフ `autoLearned`)**: 確度が高い置換だけを文字起こし終了時に適用。**original 側にも同じ置換を反映**する(しないと自分の置換を「人の修正」と数えて自己強化する)。params に autoLearned / learnApplied。再認識では自動置換しない
- **B. 用語の自動追加(既定オン `autoGloss`)**: pos≥2・ctx でない・2〜15文字の「正」を、ユーザーの用語集の後ろに足す(全体150文字以内、最大20語)。params.glossAuto に記録。文字起こしと再認識の開始時
- **C. 修正データの書き出し**: POST /api/export-corrections {tid?, audio} → zip(corrections.jsonl: doc/source(ファイル名のみ)/start/end/original/text/audio、audio/*.wav 16kHz mono、README)。最大400行・音声は1行20秒まで。同期処理・同時実行は1つ(409)。一時ファイルは送信後に削除
- 限界: neg の数え方は「1か所でも直した文字起こしは全部見直した」という仮定。前後の文字の一致は緩い判定(片側1文字)。実データでの閾値の妥当性は未検証

## 校正済み・精度測定・設定の比較(v0.7.0)
背景: 「だいぶ改善した」という体感だけでは、施策の効果を測れない。まず測定基盤を作り、学習(追加学習)の正解データの質も担保する。
- **校正済み(`proofed`)**: 各行の「聞いて確認して、文字が正しいと判断した」印(segments[].proofed=true。true のときだけ保存)。既存の「要確認の確認済み(unflag)」とは別の概念(名前が衝突しないよう「校正済み」)。UI: 行の「校正済み」ボタン / Alt+Enter(付けたら次の行へ) / 選択行・全行(全行は2度押し)/ 絞り込み(校正済み・未校正)。**聞かずに書き換えた行は外れる**: 一括置換・修正の提案の採用(画面側)、再認識(サーバー側)。結合は両方が校正済みのときだけ残り、分割は両方に引き継ぐ。文字を直接入力で直した場合は外さない(本人が確認している前提)
- **CER の測定**: GET /api/metrics?id=&legacy=1。正解=校正済みの行、機械の出力=original。NFKC・小文字化・空白/句読点/記号を除いて比較。編集距離(最小)で 置換/脱落/挿入 に分解(`lev_counts`。1まとまり 250,000 セル超は difflib で近似)。集計対象は ①両方にあり全行が校正済みのまとまり ②機械だけにある(人が行を消した=挿入の誤り。校正した時間範囲の中だけ)③人だけにある(人が足した行=脱落)。用語(用語集+置換辞書の「正」)が正しく出た率・正解に無いのに出た回数(termExtra=用語集が誘発した語尾挿入の疑い)も出す。設定別(モデル/用語集の有無/速度優先/再認識を含む)・文書別・誤りが多い場所を返す。legacy=1 は、校正済みの印が無い旧データのうち修正のある文書を全行校正済みとして仮計算(見直していない行が混じると甘くなる)
- **設定の比較(A/B)**: POST /api/abtest {tid, variants:[{model, glossary:bool}](最大4), language, device, boost, glossary, autoGloss} → ジョブ(kind=abtest、同じ待機列)。校正済みの行(最大300)の音声(前後0.3秒)を各設定で認識し直し(VAD なし・beam 5)、正解とのCER(素の出力/置換辞書後)・置換/脱落/挿入・用語ヒット・用語の誤挿入・誤りが多い行を evals/<jobid>.json に保存(最新60件)。文字起こしは書き換えない。GET /api/evals?id=(文字起こし単位) / GET /api/eval?id=。疑似モードでは、用語集あり=完全一致(+用語を余計に出す)/なし=最後の1文字が抜ける、で試験
- **英字の幻覚フラグ**: 言語が ja のとき、英字が目立つ行を要確認に(make_flags の lang/terms 引数。「英字が多い(英語の幻覚の可能性)」)。条件: 英字4文字以上・文字全体の30%以上・(英字6文字以上 or 英字の語2つ以上)、または英字と空白が8文字以上続く。用語集にある英字の語・「www」・GG/OK などは数えない。定数 LATIN_* は初期値(実データで調整する)。再認識にも効く
- **書き出しの種別**: export-corrections に scope=proofed(校正済みの行すべて。直していない行も changed=false で入る。original が無い文書も original="" で入る)。既定(scope 省略)は従来どおり直した行だけ
- 画面: 左に「認識精度の測定」カード(CER・内訳・設定別・文書別・誤り上位・A/B の設定行と結果表)
- 実データでの初回測定(v0.6 までの修正を旧データ扱いで仮計算。校正済みの印は未付与): 修正のある5クリップ(重複除外)で CER 約3.3%(正解1921字、誤り63字)。**誤りの内訳は 挿入51 / 置換8 / 脱落4 で、挿入が約8割**。挿入の大半は、機械が出して人が消した行(5行・48字。英語まじりのでたらめな文、同じ文の繰り返し、語尾に「ホロライブ」)。つまり現状の誤りは、聞き間違いより幻覚・余計な出力が主。ただし母数が小さく(約7分)、人が行を消した理由が幻覚とは限らない(クリップ端の整理など)。用語が正しく出た率は 9/14
- 検証: test_metrics.py(単体+疑似モードの通し。14件。ミューテーション5種で検出を確認)、e2e_ui_v07.py(Playwright。25項目)が通過

## 追加学習(LoRA)の計画(未着手・v0.7.0 時点の検討)
方針: 品質最優先なので、学習段階のコストはかけてよい。ただし**着手の条件**は、校正済みが2〜3時間分たまり、A/B と CER の内訳で「置換(音響の聞き間違い)」が主因と確認できてから(現状の実データでは挿入=幻覚が約8割で、学習より前処理・後処理が先)。
- 手順: ①「校正済みの行すべて(学習用)」zip を書き出す(+ 人が消した行=音声は雑音・BGM、正解は空文字、を負例として書き出す拡張が必要)②配信・動画単位で train/dev/test に分ける(行単位で分けると同じ配信の声が漏れて評価が甘くなる)③クラウドGPU(Colab / RunPod 等。自PCは AMD で不可)で HF Transformers + PEFT の LoRA 学習(large-v3-turbo か large-v3 が候補)④LoRA を統合(merge_and_unload)→ CTranslate2 に変換(ct2-transformers-converter、int8 か float16)→ models/custom/<名前>/ に置く⑤ツール側: モデル名 `local:<名前>` を models/custom/ 配下の存在確認つきで受ける(パス指定を許さない。MODEL_RE と同じ方針)⑥A/B で、学習に使っていない配信の校正済み行を使い、基準モデルと CER・用語ヒット率・挿入(幻覚)・タイムスタンプのずれを比べ、勝ったときだけ採用
- メリット: 推論の重さが増えない(統合後は同じ大きさで、CPU でも動く)/ 音響面(早口・笑い声・ゲーム音混じり・声の重なり)と固有名詞を音から覚える(辞書のような同音異義語の誤爆が無い)/ 負例を入れれば幻覚の抑制も期待できる
- デメリット・リスク: 正解データの校正が最大の手間(数時間分)/ 少量だと過学習・忘却(学習に出ていない配信者・話題で悪化しうる。学習に出ない名前は直らない)/ タイムスタンプの劣化(タイムスタンプ無しで学習すると字幕の時刻に響く。時刻つきで学習するか、dev で確認)/ クラウドへの音声アップロード(配信者・出演者の声と会話。権利・規約・同意の確認が要る。公開しない・終わったら消す)/ 費用と環境構築の手間、モデル更新のたびに再学習 / 効果は保証されない
- 学習の判断は、必ず A/B の数字で行う
