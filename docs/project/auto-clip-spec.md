# 自動切り抜き v0.1.1(開発メモ)

**第1のゴール(ユーザー指定): 配信の中の盛り上がっている部分を自動で切り抜いて出力する。** ローカルWebアプリ(serve.py + index.html、標準ポート8795、Python標準ライブラリのみ。外部ツール: ffmpeg、YouTube入力には yt-dlp)。

## ユーザーの選択(確認済み)
- 盛り上がりの材料: 音声 + チャットのリプレイ + 動画コメント欄のタイムスタンプ(3つとも)
- 入力: YouTubeのURL(実装では「手元のファイル」も追加。音声だけで判定。テスト・保険用)
- 出力: 区間を自動決定して mp4 を書き出す(横のまま。縦9:16は未対応)

## 設計
- 素材: yt-dlp で音声(-f ba/b)、チャットは `--skip-download --write-subs --sub-langs live_chat`(chat.live_chat.json。JSONL、replayChatItemAction/videoOffsetTimeMsec)、コメントは Data API commentThreads(relevance、最大5ページ=5ユニット、任意)
- 音声: ffmpeg の astats+ametadata で1秒ごとの RMS(dB)。全帯域と、2kHz以上(笑い声・叫びが目立つ帯域)の2系列
- 点数化: 各系列を「ふだん(前後150秒の中央値。10秒ごとに求めて補間)からの偏差 ÷ 偏差のMAD×1.4826(下限つき)」で無単位化、上限6。チャットは log1p(10秒平均の活気)で同様に、反応の遅れ補正(既定8秒)だけ前へずらす。コメント欄は時刻±20秒にガウス状の山(いいね数で強さ)
- 合計 = 重み付きの和(音声1.0・チャット1.0・コメント0.7)。材料が重なるほど高い
- 区間選び: 5秒平滑化した合計の最大値を貪欲に選び、山を区間の65%に置く(既定45秒)、端を±4秒内の最も静かな秒へ合わせる(長さ±30%以内・山を含む場合のみ)、選んだ区間±5秒は除外。閾値は感度(高1.2/標準2.0/低3.2)
- 出力: YouTube は yt-dlp --download-sections + --force-keyframes-at-cuts、ファイルは ffmpeg で再エンコード(libx264 crf20)。clips/<動画ID_日時>/NN_開始-終了_sスコア.mp4 と clips.json(元のパスは含めない)。長さが±4秒以内か検証
- 画面: 材料の選択、本数・長さ・感度、盛り上がりのグラフ(SVG)、候補一覧(開始・終了を編集して個別に書き出し直し、プレビュー動画)。「見つけたらそのまま書き出す」をオフにすると確認してから書き出せる
- セキュリティ: 127.0.0.1のみ、Host/Origin/Sec-Fetch-Site検査、URLは youtube.com/youtu.be の11文字IDのみ受け付け(引数注入・偽ドメイン拒否)、ファイルは拡張子検査、/clip は clips/<フォルダ>/<名前>.mp4 の2階層だけ(realpath検査)、ログのURLは伏せる、CSPメタ、APIキーは config.json(0600)
- 1度に1ジョブ(409)。中止は子プロセスを terminate。解析結果はメモリ内(サーバーを閉じると消える)

## v0.1.1: チャット取得が遅い問題への対応(ユーザー報告)
- 原因の見立て(実機では未確認): yt-dlp の live_chat 取得は配信の長さに比例して連続リクエストを順番に行うため、長い配信では数分〜十数分かかる。v0.1.0 は音声の解析が終わってから取得を始め、進捗も出さず、上限30分だった。yt-dlp 側の取得自体は速くできない
- 対応(待ち時間を減らす・見せる・切る):
  1. **並行取得**: 解析開始と同時に別スレッドでチャット取得を始める(音声のDL・解析と重ねる)。run_capture に slot 引数(proc/proc2)を追加し、中止は両方の子プロセスを止める。途中で失敗・中止したときも finally で後始末
  2. **キャッシュ**: 完走(終了コード0)したチャットは cache/chat/<動画ID>.live_chat.json に保存(最新30本まで)。同じ動画の再解析では再取得しない(警告欄に「前回の取得分を再利用」)。時間切れ・スキップで打ち切ったものは保存しない
  3. **待ち時間の上限**を設定化(chatTimeout、1〜120分、既定20分)。超えたらチャットなしで続行(警告あり)。run_capture に watchdog スレッドを追加(yt-dlp が無出力でも時間切れ・中止で確実に止まる。v0.1.0 は出力行が来たときだけ判定していた)
  4. **「チャットを待たずに進める」ボタン**(/api/job/skipchat): 音声・コメントだけの結果を先に出せる
  5. 進捗: 画面に「チャット取得: 並行して実行中 m:ss」、待ち状態では経過時間を表示。job.chat に state/elapsed/bytes(出力ファイルの大きさ)を公開
- 不採用: YouTube の内部チャットAPIを直接叩いて並列化する方法(非公式・仕様変更や規約のリスクが高く、この環境では検証もできない)
- 検証: test_chat.py(偽 yt-dlp で非FAKEの経路を検証: 3秒+3秒が並行で完了、キャッシュ再利用、時間切れ、スキップ、チャット失敗でも続行、中止、子プロセス・作業フォルダの残りなし、chatTimeout の範囲) と e2e_skip.js(ボタン表示→スキップ→候補表示)。既存の test_ac.py / e2e_ac.js も通過
- **未検証**: 実機の yt-dlp でどれだけ短縮されるか(並行化で音声解析の時間分は隠れるが、チャット取得自体の所要は変わらない)。yt-dlp が live_chat 取得中にどんな出力をするか(進捗は経過時間と出力ファイルの大きさで代用)
