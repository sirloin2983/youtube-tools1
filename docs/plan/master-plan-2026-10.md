## 2. 原則(この計画の全段)
1. **記録は今すぐ、改善は量がたまってから**。データは使った日からしか貯まらない。記録の仕組み(段 Q2)は改善より先に入れる
2. **使えば勝手に貯まる**。評価のためだけの作業を減らし、普段の校正・判定・カットの直しをそのまま正解にする
3. **機械の最初の結果は書き換えない**。人が直した最終と並べて残す(今は話者・カットのたたき台が上書きされて残らない = 下の 3)
4. **時期で分けて測る**: ある日までのデータで学習・調整し、その後のデータで測る。毎週の新しい校正が、そのまま次のテストになる。
   ただし人は機械の下書きにつられる(迷うと直さずに通す)ので、普段のデータは「下書きを作ったエンジン」に甘く出る → **小さな定点の評価用**(丁寧に校正した 15 分前後。辞書・学習に使わない今の決まりのまま)を長い期間の比較とエンジンの比較の最終判断に使う
5. **測ってから採る**(今までどおり)。採用の決まりは線 B の 1回目と同じ形(悪化の側に 95% の範囲が出ない・余分が増えない・名前の再現率が下がらない)を各領域に合わせて決める
6. 重い処理は `ytt_core/jobs.py` の SLOTS、認識のネイティブコードはワーカーの中だけ、外へ音声・動画を送らない(今の決まりのまま)

## 4. どれが文字起こしに頼るか(実装の時期の考え方)
```
                      ┌─ 話者(行の時刻は人が直したものを使えば、文字の正しさに頼らない)…… 早く始められる
文字起こしの精度 ─────┼─ カット「行から」(抜けがあると声を切る。行の端の時刻が効く)…… 段3「抜け」のあと
(エンジンの決定 →     ├─ 字幕の分け方(単語の時刻がエンジンで変わる)…… エンジンの決定のあと
 抜け → 聞き違い)     └─ 盛り上がりの「言葉の材料」(候補の区間だけ文字起こしして並べ替え)…… エンジンの決定 + GPU のあと
カット「無音」・盛り上がりの「音とチャットの材料」・話者の声の照合 …… 文字起こしに頼らない = いつでも
```
- **盛り上がりの言葉の材料は「全部を文字起こし」しない**。配信全体(数時間)は CPU で数時間かかる。音とチャットで候補を出したあと、**上位の候補の区間だけ**(例: 30 個 × 60 秒 = 30 分。GPU なら数分)を文字起こしして並べ替える二段にする。
  笑い・叫び・呼びかけの語が拾えれば足りるので、エンジンの決定(段 I-1a)のあとでよく、抜け・聞き違いの改善(I-1b 以降)は待たない
- 話者は「人が時刻を直した行」に対して測れば、文字の誤りに引きずられない → 文字起こしの改善と並べて進める
- カットの「行から」は、行が抜けた所を切ってしまうのが一番の害。抜けを減らす段(I-1b)のあとに調整する。それまでは無音カットと余白を先に直す

### Q1 30fps にそろえる(M・線 A の新しい段)
- 共通の部品 `ytt_core/normalize.py`: ffprobe で調べ、**H.264・8bit・yuv420p・30/1 の固定(CFR)・AAC** ならそのまま(作り直さない)、違えば ffmpeg で作り直す(`-vf fps=30`・`ENC` と同じ画質の設定)。SLOTS を通す。
  時刻は秒のまま保たれる(文字起こし・マークの時刻はそのまま使える)。29.97 → 30 は約 33 秒に1コマ重なるが目立たない
- 入口ごと:
  - スタジオの書き出し: `ENC` に fps=30 を足す。YouTube の区間取得は「yt-dlp で区間をそのまま取る(作り直さない・少し広め)→ `ENC` で正確な区間に切って 30fps に」の2段にする(今は yt-dlp 任せの作り直しで、画質の設定 crf 18 を通っていない)。
    「高速」はコピーでは fps を変えられないので、**速い設定(preset ultrafast)での作り直し**に変える
  - 依頼の受付(`home/intake.py`): コピーしたあとに normalize(作業データの intake の中の写しを置き換える。友人の元のファイルは今までどおり残る)
  - 「編集」の単体の文字起こし・付け替え: 30fps でなければ、元の動画の隣に `<名前>_30fps.mp4` を作り、文書はそれを指す(元は消さない。作れない場所なら案内して止める)
  - 友人用簡易版: ドロップ・「ファイルを選ぶ」のどちらも `lite-media/` に 30fps の写しを作って使う(友人の PC の CPU で作り直す。切り抜きは短いので数十秒の見込み)
  - 線 D(リアルタイム切り抜き): 録画は 60fps のまま、書き出しで normalize(後工程は同じ)
- 後ろの処理: パックの fps の選択肢を畳む(30 固定)・60↔30 の注意を消す・Lua で「素材が 30fps か」を確かめて違えば止める。
  **どの fps でも動く今のコード(保存形式の `sources[].fps`・Lua の換算)は保険として残す**(以前の文書・テストのため。消す利益が小さい)
- テスト: exporter の 30fps のテストを新しく。60fps を前提にした約 15〜20 件を「60fps の素材 → 30fps に作り直される」に直す
- 友人に渡し直すもの: 簡易版を使う友人には新しい start 一式(送るアプリは変えない)

- `dev/eval_asr.py`: 時期で分ける(`--since`)・普段の文書もエンジンの比較に使う(ヒントなしで認識し直す)・友人の zip(`eval-intake/works/`)も読む

## 8. リスク
- **下書きへのつられ**: 普段のデータは下書きを作ったエンジンに甘い → エンジンの比較の最終判断は定点で。普段のデータは「同じエンジンのまま設定や辞書を変えたとき」の比較に主に使う
- **時期で分けたときにエンジン・設定が途中で変わる**: 文書ごとにエンジン・設定・辞書の版を残し(Q2)、変わった前後を混ぜて比べない
- 少ないデータで決めすぎる: 各領域で最低の量(例: 話者は 200 行・盛り上がりは配信 10 本)に届くまでは、測るだけで既定値を変えない
- 30fps の作り直しの時間と画質: 1回だけの作り直し(スタジオの精密はもともと作り直している)。区間取得の2段化で yt-dlp 任せの作り直しが無くなり、画質の設定はむしろそろう
- 作業データが増える: 記録は小さい(JSON)。評価用の flac は数百 MB。バックアップの容量は「調子」の画面で見る
- 担当: 全段 Claude Code(PC)。`editor/`・`studio/`・`home/`・`cut2resolve/`・`ytt_core/` に及ぶので、他の AI の作業途中と重ならないよう、始める前に `git status` と WORKLOG を見る
