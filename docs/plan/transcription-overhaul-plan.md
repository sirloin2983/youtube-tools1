## 3. 外の状況(2026-09-27 の調査。出典は末尾)
- **公開の比較で強いのは Qwen3-ASR-1.7B**(実メディア 20 本で CER 0.140。large-v3-turbo 0.184、kotoba-whisper-v2.0 0.495)。
  **文脈(用語の一覧)をプロンプトで渡して寄せられる** = 呼び名対策の本命。Apache-2.0。時刻は別モデル Qwen3-ForcedAligner-0.6B(日本語対応)
- 固有名詞の正しさは Whisper 0.60・Qwen3 0.58 が上位。Parakeet・ReazonSpeech・kotoba は 0.15〜0.25 と弱い(CER が低くても名前に弱いモデルがある)
- anime-whisper(MIT)は感情のこもった声に強いが、**プロンプトを入れると大きく悪化**(呼び名は後処理でしか効かせられない)
- **VTuber・配信の音声で測った公開データは無い** → どのモデルが良いかは、**手元の評価セットで測るしかない**
- AMD GPU(Windows・RX 7800 XT)で実用になる経路は2つだけ:
  **whisper.cpp の Vulkan 版**(Whisper 系・anime-whisper を ggml に変換。VAD(Silero v6.2)・プロンプト・トークンの時刻・温度のフォールバックあり)と、
  **llama.cpp の Vulkan 版**(Qwen3-ASR の GGUF。**文脈のプロンプトが効くかは未確定**)。
  DirectML は新機能が止まり、WinML は Windows 11 24H2 以降(この PC は 23H2)、CTranslate2 の ROCm 版は Windows で DLL が合わず、PyTorch ROCm は RX 7800 XT が公式の一覧に無い
- BGM の分離を**認識の前に入れると悪化する報告が多い**。良かったのは「分離した声を VAD(声のある所の検出)に使う」方法
- 2つの認識の多数決(ROVER)は日本語で伸びが小さい(CER 3.0 → 2.9)。抜けには「声があるのに文字が無い所を別のモデルで埋める」方が効く見込み
- 重なり声: 分離モデル(MossFormer2・pyannote の分離)は英語中心で日本語の配信での性能は未知。**別視点(相手の配信)で聞き直すのが確実**(その人のマイクの声がいちばんきれい)

## 5. 段階(上から順。段ごとにテスト → WORKLOG → コミット → 中間報告。各段の始めに変えるファイルと依存をユーザーに確認)

### 段0 測る土台(依存なし・すぐできる・この計画の前提)
- 0-1 **信頼度を残す**: `original` の各行に avg_logprob・no_speech_prob・compression_ratio、words.json の単語に確率を足す(任意の項目。古い文書はそのまま開ける)
- 0-2 **評価の道具** `dev/eval_asr.py`: 評価セットの音声(校正済みの行)を、指定したエンジン・設定で認識し直して、
  CER(置換・抜け・余分)・条件別(重なり・BGM・印あり)・呼び名の再現率・かかった時間を JSON に残す。**文書は書き換えない**。
  画面の「設定の比較(A/B)」とは別に、エンジンを増やしても同じ物差しで測れるようにする
- 0-3 **比べるときの正規化**: つなぎ言葉・数字・笑い・伸ばしの書き方(`docs/plan/accuracy/USER_INPUT.md` の 7)を決め、評価で同じ規則にそろえる
- 0-4 モデルを取得済みならオフラインで読む(版の確認の通信をやめる)
- **ユーザーの作業(ここがいちばんの律速)**: 評価用を **合計 15〜30 分・話者 4 人以上・元の配信 3 本以上**、特に**重なり声(コラボ)・BGM の大きいゲーム・呼び名の多い場面**を校正する。
  AI は候補の場面の一覧を作る手伝いまで(未校正の評価用 4 本を校正すると約 3 分増える)

### 段1 呼び名と配信ごとの文脈(依存なし・効果大の見込み)
- 1-1 **名簿に呼び名**: `hololive-roster.json` のメンバーに `aliases`(フブキ・フブちゃん・白上 など)と「誤りやすい形」(トーイ→トワ)。
  AI が下書きを作り、**ユーザーが確かめて直す**(`USER_INPUT.md` の 1・2。普通の言葉と重なる呼び名(みこ など)は置換の対象から外す印)
- 1-2 **配信ごとの文脈を自動で作る**: 配信者(スタジオの data.json の channel)・配信の題名に出るメンバー名・コラボ相手から、その配信に出る人の名前と呼び名だけを選び、
  認識のプロンプト(faster-whisper は initial_prompt・hotwords、Qwen3 は文脈)に渡す。今は用語集が空なので何も渡っていない。
  入る長さに限りがある(先頭 約150字)ので、出る人に絞るのが要
- 1-3 **出る人に限った置き換え**: 修正から学んだ「誤→正」を、その人が出る配信の文書だけに効かせる(一律の置換で普通の言葉を壊さない)
- 測り方: 段0 の道具で、プロンプトなし/ありの CER と呼び名の再現率を比べる。**悪くなるモデル(anime-whisper)には渡さない**

### 段2 エンジンを差し替えられるように + GPU(新しい実行ファイル・モデル)
- 2-1 **エンジンの境界**(v2 設計書の Phase 1): 認識ワーカー(`tx_worker.py`)の中に「エンジン」の口を作り、今の faster-whisper をその1つにする。
  **出力が1文字も変わらないこと**をテストで確かめてから次へ。サーバー側は今の `RemoteModel` の形のまま(numpy などをサーバー側で読まない決まりは変えない)
- 2-2 **whisper.cpp Vulkan**(実行ファイルを子プロセスで。取得は URL・SHA-256 固定・版を記録)。GPU を使っていることを確かめる・Vulkan が使えないときは**黙って CPU にしない**(理由を出す)。
  large-v3・turbo・anime-whisper(ggml)を GPU で動かせるようになる
- 2-3 **Qwen3-ASR**: まず手早く動く経路(sherpa-onnx の 0.6B int8 を CPU、または llama.cpp の Vulkan で 1.7B の GGUF)で試し、**文脈のプロンプトが効く経路**を確かめる。
  時刻は Qwen3-ForcedAligner(単語の時刻 → 今の行の分け方・words.json に載せる)
- 2-4 **比べて決める**: 段0 の評価セットで large-v3(今)・turbo・anime-whisper・Qwen3-ASR-1.7B(文脈あり)を、CER・呼び名・抜け・重なり・時間で比べ、
  **主のエンジンと2つ目のエンジン**をユーザーと決める。クラウド(gpt-transcribe など)は**ここで1回だけ**比較に使う(評価用 30 分 × 数回で数十〜数百円。送る前に秒数と見積もりを出して確認・API キーは環境変数・結果は保存して再送しない)

### 段3 抜けを減らす
- 3-1 **「声があるのに行が無い」区間を見つける**: VAD(Silero v6.2)で声がある所と行の時間を比べ、行が無い・ごく短い所に新しい印「声があるのに字幕が無い」を付け、
  ③-2 の「疑わしい所だけ認識し直す」の対象に入れる(今の「長い区間に文字が少ない」と同じ流れ)
- 3-2 **認識し直しに2つ目のエンジンを使う**: 同じモデルで同じ所を聞き直すより、別の系統のモデルの方が違う間違い方をする。良くなったかの判定 `redo_better` に「2つのエンジンの一致」を足す
- 3-3 **BGM が大きい所は、分離した声を VAD にだけ使う**(認識には元の音声を入れる。分離を認識の前に入れると悪化した報告が多いため)。分離は audio-separator の MDX 系(AMD GPU は試験的・CPU でも可)。
  **段0 の評価で効いたときだけ**入れる
- 3-4 温度のフォールバック・音声でないトークンの抑え方などの設定を、評価セットの dev 側で調整する(test 側で決めない)

### 段4 聞き違いを減らす(2つのエンジンの食い違いを使う)
- 4-1 2つ目のエンジンで全体も認識できる速さになったら(GPU)、2つの結果を文字の位置でそろえ、**食い違う所に印と「もう一方の候補」**を付ける。
  校正では候補を1押しで採れる(自動で置き換えるのは、候補が名簿の呼び名と一致するときだけ。それ以外は人が選ぶ)
- 4-2 (任意・後回し)ローカルの LLM(llama.cpp の Vulkan)に「候補のどちらか」を選ばせる。自由に書き直させない(悪化しやすい)。名前の選択に絞る

### 段5 重なり声
- 5-1 **重なった所を見つける**: 話者判別の結果の重なり・2つのエンジンの食い違い・「声が重なる」のメモから、重なりの区間を出す
- 5-2 **別視点で聞き直す**(本命): コラボ相手の配信の URL を切り抜き(案件)に登録 → 重なった所の前後だけを yt-dlp の区間指定で取得 →
  共通して聞こえる声で時刻を合わせ(相互相関。区間ごとに毎回)→ その人の視点の音声で認識し直す。スタジオのコラボの情報と共有する(`docs/archive/project/collab-mark-spec.md`)
- 5-3 (試験)別視点が無いときは、重なった区間だけ声の分離(MossFormer2 の ONNX など)→ それぞれ認識 → 元の結果と比べて良いときだけ採る

### やらないこと(この計画の中では)
- モデルの追加学習(LoRA など)。校正済みが数時間分たまってから改めて検討
- 常時のクラウド認識・自動の送信・全編への音源分離・全視点の全文認識・LLM による文章の書き直し
- 保存形式の壊れる変更(`transcribe/v1` に任意の項目を足すだけ)・serve.py / app.js の全面の書き直し

## 7. 守ること(この計画の全段)
- 認識のネイティブコード(faster-whisper・whisper.cpp・llama.cpp・sherpa-onnx・分離)は**認識ワーカーの中か子プロセスだけ**。サーバー側で numpy などを import しない(`editor/tests/test_worker.py`)
- 重い処理は `ytt_core/jobs.py` の SLOTS を通す。GPU のモデルは同時に1つだけ読み、切り替えるときは前のものを手放す(VRAM 16GB)
- 取得する実行ファイル・モデルは URL・大きさ・SHA-256 を固定。外部コマンドは引数のリストで渡し、shell を使わない。モデル名から任意のパスを作らない
- クラウド: 既定オフ・キー未設定でも全部動く・送る前に対象と見積もりを確認・評価用を送るときは別に確認・ログに字幕の全文とキーを出さない
- 機械の出力 `original` と人が直した `segments` の意味は変えない。新しい情報は任意の項目(v2 設計書の 7 の `recognition.runs` の形)
- 版は serve.py・app.js・README の3か所を同時に上げる

### 1回目の結果(2026-09-29 Claude Code。編集 0.22.0)
- 手順0: 評価用を配信者単位で入れ替えた(スバル・ルイ・ロボ子の文書は全部評価用。フブキ02・03 は外した)。評価用 21 本・9.9 分・6 人 / 学習用 8 本・2.6 分。記録は `docs/archive/project/eval-set-procedure.md`
- 段1-1: `editor/hololive-roster.json` の `members`(aliases・common・misrecognitions)。呼び名は AI の下書き(ユーザーの確認待ち)。誤りやすい形は学習用の修正に出るものだけ
- 段1-2: `serve.py` の `stream_context`(チャンネル名・コラボ相手・話者の名前・題名とフォルダ名 → 出る人 → 名前 + 呼び名 3 つ)。設定 `autoContext`(既定オフ)。評価用として文字起こし(`evalSet`)。

- S-3: `make_flags` の `stock_phrase`(HALLUC_LINE・音楽の表記)・`repeats_in_line`・近くの同じ文・`LEAK_FLAG`。声の検出のやり直し・緩い条件の認識・`redo_better` もこれに合わせた

### 3回目の結果(2026-10-02 Claude Code。編集 0.36.0)— 段2-2 whisper.cpp Vulkan
- 8 の 4 の決定: whisper.cpp は公式の配布に Windows の Vulkan 版が無い → **公式のソースを決まったコミット(v1.9.4 = 927cfce3)で取り、この PC で作る**(`setup/build-whisper-vulkan.bat`。Vulkan SDK はユーザーが winget で入れる)。
  llama.cpp(2-3)は公式の win-vulkan-x64 の zip を URL・SHA-256 固定で取得してよい
- 分かったこと: ① MSBuild は 260 文字を超えるパスで失敗する → 作るのは `C:\ytt-build\`(できたら消す)② RX 7800 XT + AMD のドライバでは行列コア(KHR_coopmat)の経路で落ちる → `GGML_VK_DISABLE_COOPMAT=1`
  ③ whisper.cpp の声の検出は声の所をつないで認識するため、文字が大きく抜けた(turbo で CER 36% → 80%)→ 既定で使わない
- 測った結果(評価用 18 本・1,229 秒・温度 0・文脈なし。同じ文書でそろえた):

  | エンジン・モデル | 機器 | CER | 置換 / 抜け / 余分 | 認識の秒 |
  |---|---|---|---|---|
  | faster-whisper large-v3(声の検出 弱め) | CPU | **21.7%** | 141 / 468 / 102 | 900 |
  | whisper.cpp large-v3(声の検出なし) | GPU | 27.0% | 223 / **243** / 415 | **180** |
  | whisper.cpp large-v3-turbo(声の検出なし) | GPU | 36.4% | 285 / 266 / 641 | 86 |

  温度 0 では、whisper.cpp の余分な文字が多い。ただし多くは声の無い所の幻覚ではなく**同じ文字の繰り返し**(「うううう…」)。温度 0 = `-nf` で、やり直しが止まるため
- 続き(ユーザー決定「1」): 全体を認識 → Silero で声の無い所の行を捨てる案は**悪化**(27.0% → 33.8%。抜け 243 → 588。BGM・ゲームの音で Silero が声を取りこぼす)→ 既定オフ(`TRANSCRIBE_WCPP_SPEECH_FILTER=1` で測れる)
- **温度のやり直しあり(アプリで普段使う形)で比べた結果**(同じ 18 本):

  | エンジン・モデル | 機器 | CER(95% の範囲) | 置換 / 抜け / 余分 | 認識の秒 |
  |---|---|---|---|---|
  | faster-whisper large-v3(声の検出 弱め) | CPU | 21.1%(15.3〜28.5) | 150 / 439 / 104 | 561 |
  | whisper.cpp large-v3(声の検出なし) | GPU | 21.6%(17.5〜27.3) | 187 / **248** / 272 | **130** |

  精度は誤差の範囲で同じ・GPU は約 4 倍速い。誤り方が違う(GPU は抜けが少なく余分が多い)。
  **測るときの注意**: whisper.cpp を温度 0(`--temp0`)で測ると繰り返しで大きく悪く出る。エンジンを比べるときは「やり直しあり」を複数回か、量で比べる
- 次の候補: ① whisper.cpp を主のエンジンにする(画面で選べるように。速さが主な利点。採るかはユーザーと決める)
  ② 2-3 Qwen3-ASR(llama.cpp の Vulkan)③ 抜けの少なさを段3「声があるのに行が無い所」の2つ目のエンジンとして使う(誤り方が違うので相性がよい見込み)
