## 4. おすすめの順番と理由
```
(実際の Dropbox の確認 → 出た直し)
段5 → 段6 → 段9 → 段10 → [線 B 段1・段2 を入れる切れ目] → 線 C の土台(旧 段11) → 段12 → 段8 → 段15   (段13・段14 はやらない。10-01 決定)
```
- **段9 を段8 より先に**: 依頼の受付が動き始めると、裏で自動で動く時間が増える。壊れたときに何が起きたか画面で分かること(調子・容量・記録)が、新しい機能より先に要る
- **段10 を線 B 段2 の前に**: 線 B 段2〜5 は `serve.py` の認識の部分を大きく書き換える。分けてからの方が、線 B の差分が小さく・テストが速く・AI 間の競合も減る。逆に線 B のあとに分けると、動いている認識のコードを2度触ることになる
- **段13 を段11 より先に**: 段13 は既にあるデータ(文字起こし・マーク)で作れて、毎回の投稿の手間をすぐ減らす。段11 は評価データが貯まるまで効果を測れない(線 B と同じ構造)
- **段8 は後ろのまま**: 使うのがまれ(09-29 決定)。段13・段11 で案件の形が固まってからの方が、複数の素材の扱いも決めやすい
- **段14 は決めてから**: パックの契約(Resolve に渡す形)の外側に「完成品を作る」を足す大きな変更。友人が Resolve を持っているかで要否が変わる

## 5. 各段の概要(目的・含まない・リスク・決めてもらうこと)

### 段9 運用の安定化
- 目的: 裏で自動で動く(依頼の受付・まとめて実行)ものが増えたので、**止まった・失敗した・容量が無い**を画面で分かるようにする
- 含まない: 自動で消す(片付けは候補を出して確認)。外部への通知(メール・LINE)は含まない(友人への知らせは Dropbox の `出力\` に結果のファイルを置く形)
- リスク: 「起動し直す」は入口が自分を起こし直す = 子プロセスの後始末(SIGBREAK の約束)と `.runtime` の扱いに絡む。`home/launch.py` のテストを必ず通す
- 決めてもらうこと: 片付けの対象(exports の元動画を消すか。パックは残すか)・依頼の受付の上限(1日 N 本・1本 N GB)

### 段10 コードの整理
- 目的: `editor/serve.py` を役割で分け、線 B の書き換えとテストを楽にする。**動きは変えない**(版も上げない。契約テスト・e2e が全部そのまま通ることが終わりの条件)
- 含まない: フレームワーク・ビルドの導入(DESIGN_BRIEF で Out of Scope)、画面の見た目の変更
- リスク: 分割の途中で他の AI が同じファイルを触ると衝突する → **担当を宣言して1〜2 セッションで一気に**、項目ごとにコミット。`home/tests/test_mount.py` の「同じ名前の .py を作らない」に注意(分けたモジュール名)
- 決めてもらうこと: 線 B 段1(呼び名。serve.py を触る)を段10 の前にやるか後にやるか(おすすめ: 前。小さい差分なので)

### 段11 見どころ検出の精度(線 C)
- 目的: 「採用された区間」を正解として、自動マークの点数の付け方を測って直す。線 B と同じく「測る土台 → 1つずつ試す → 効いたものだけ採用」
- 含まない: 学習モデルの導入(まずは重みと特徴の見直し)
- リスク: 採用の記録が少ないと過学習する(配信者・配信タイプごとに偏る)。件数の目安を最初に決める(2026-10-03: 入れ直しで採用の記録は 0 に戻った。貯め直す)
- 決めてもらうこと: 評価に使う配信の範囲(全メンバーで広く = `clips-all-hololive-jp` の方針と同じ)・線 C として ROADMAP に独立させるか

### 段12 コラボ・別視点
- 目的: コラボ配信の別視点(相手側の配信)を、ズレを自動で合わせて使えるようにする。線 B 段5(重なり声)が別視点の音声を使う設計なので、その土台を兼ねる
- 含まない: 別視点の動画の自動取得(URL はユーザーが入れる)
- リスク: ズレが一定でない(回線落ち・広告)配信は区間ごとのズレになり、データの形が変わる。段8 の「素材ごとの区間」と形を合わせる
- 決めてもらうこと: 線 B 段5 と一緒にやるか(そのときは線 B の段として扱う)

### 段13 投稿の準備
- 目的: パックのあと、YouTube に上げるまでに手で書いているもの(タイトル・説明・ハッシュタグ・チャプター)を型から作って、案件に残す。投稿済みの完成品も案件から辿れる
- 含まない: YouTube への投稿そのもの(Data API の投稿は審査と費用がある)、文章の生成(LLM)。型の例: 「【配信者】見出し(元の配信の題名)」+ 出典の URL + 「切り抜き元: …」
- リスク: 案件の形(`home/cases.py`)に欄が増える。古い案件のファイルを壊さない(欄が無ければ空)
- 決めてもらうこと: 型の中身(今、実際に書いている説明文の形をもらう)・サムネの候補が要るか

### 段14 Resolve なしの仕上げ(要決定)
- 目的: 字幕を焼き込んだ mp4 を ffmpeg で作る(粗編集の動画 + 字幕)。友人の ① 全自動が「完成品」を返せる
- 含まない: 縦動画(9:16)への変換(09-26 やらない)、Resolve と同じ見た目の Text+(字幕の見た目は簡素な1種類)
- リスク: 「パックは cut2resolve/pack.py だけが作る」の決まりの外側に出る。字幕の見た目が Resolve と違うと「どちらが本物か」で混乱する → 名前を「簡易の完成品」と分ける
- 決めてもらうこと: **やるか・やらないか**(友人が Resolve を使うなら要らない)

### 段15 画面と周辺の残り
- 目的: 段5 のあとに残る細かい不揃いと、ホロカラーの「この先の案」を片付ける
- 決めてもらうこと: 暗いテーマを既定にするか(今は Out of Scope)・ホロカラーの「他のグループの JSON」が要るか(友人の要望次第)
