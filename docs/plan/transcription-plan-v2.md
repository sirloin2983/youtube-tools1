## 0. なぜ書き直したか(10-04 に全部を読み直して見つけたこと)
1. **データがほぼ 0**。10-03 の入れ直しのあと、評価用は 3 本(確かめ済み 0 本)・普段の文書は 3 本(校正済みの行 0)。残りの段はすべて「定点 15 分」を待っていて、AI 側が止まっている
2. **15 分では小さな差が見えない**。以前の約 20 分の測定でも CER の 95% の範囲は 15〜28% と広かった。「15 分そろえば全部決められる」という作りが甘い
3. **校正が律速なのに、校正を速くする機能が最後にあった**(2つのエンジンの食い違いの印と候補 = 第1版の段4)
4. **抜け落ちた項目**: クラウドの文字起こしとの比較(段2-4)・出る人に限った置き換え(段1-3)・anime-whisper と turbo の比較・クラウド GPU での追加学習(最初の仕様では「費用をかけてよい」だった)
5. **評価用の材料が多すぎる**。仮置きの 360 本(3 時間 42 分)が全部評価用で、学習にも辞書にも使えない
6. **仮置きの 360 本は完成したショート動画**(10-04 に確かめた: 縦 1080×1920・30fps・DaVinci Resolve の書き出し・字幕と題名が焼き込み・29 人・平均 37 秒)。
   ツールが普段文字起こしするのは**編集前の切り抜き**なので、音が違う(詰めたカット・効果音・BGM が足されている場合がある)。定点だけで決めると、普段の素材とずれるおそれがある

## 2. 原則(第1版から変えた所)
1. **量の関門で区切る**。たまった量で「決めてよいこと」を分ける(下の 3-2)。見えない差は「分からない」と書き、既定を変えない
2. **校正を速くするものを先に作る**。校正の速さが全部の段の速さを決める
3. **物差しは 2 本**: 定点(ショート。丁寧に全部聞いた正解・エンジンに甘くない)と、普段の校正(編集前の切り抜き。時期で分ける・下書きのエンジンに甘い)。**2 本が食い違ったら採らない**
4. **効きめの大きい順**。名前の聞き違いは、ヒント(悪化した)より先に「食い違いの候補」と「追加学習」で狙う
5. 今までどおり: 測ってから採る・評価用は学習と辞書に使わない・機械の最初の結果は書き換えない・認識のネイティブコードはワーカーか子プロセスだけ・重い処理は SLOTS

## 3. データの設計

### 3-1 360 本の分け方(段 D0)
- 単位は **メンバー × 日付**(同じ単位は必ず同じ側。同じ配信が両方に入らないように)
- **評価用(ショートの定点)約 30 分**(10-04 に 60 分から変えた: 編集前の定点を配信から取得して主にするため = 3-3)。人ごとに偏らないよう、2 単位以上ある人には必ず 1 単位入れる。
  文字起こし済みの動画(文書がある)と、名簿に無い人(`教師データ＿如月れん` の 7 本 = 知らない声での確認)は評価用に固定
- **10-04 に作った一覧**(`<評価用のフォルダ>\split-plan.json`。`dev/eval_split.py plan`): 評価用 47 本・31.4 分 / 学習用 313 本・190.6 分(3 時間 11 分)
- **学習用**。評価用のフォルダの外の新しいフォルダ(案: `E:\Video\切り抜き動画素材\学習用データ\`)へ移す。
  評価用のフォルダの中にある限り評価用の印を外せないため、移すしかない
- 手順: AI が分け方の一覧(どの動画がどちら)を作る → ユーザーが見て直す → 道具が移す(文書があれば付け替える)。分け方は一覧のファイルに残し、あとから変えない
- 定点の進め方は今のまま(評価ドリル。乱数で 1 本ずつ)。学習用は普通の校正(用語集・辞書・候補を使ってよい)

### 3-2 量の関門
| 関門 | 条件 | 決めてよいこと |
|---|---|---|
| G0 | 定点 5 分 | 道具が正しく動くかの確認・大きな悪化(10 ポイント以上)の検出だけ |
| G1 | 定点 15 分 + 今の条件(話者 4 人・配信 3 本・重なり 30 秒・BGM 30 秒・呼び名 10 行) | 主のエンジンと 2 つ目のエンジン・クラウドとの比較 |
| G2 | 定点 30 分 + 普段の校正 30 分 | 中くらいの差(5 ポイント前後)の施策: 抜けの対策・ヒントのやり直し |
| G3 | 定点 60 分 | 小さな差(2〜3 ポイント)の調整・追加学習したモデルの採否 |
| FT | 学習用の校正済み 3 時間(評価用を除く) | 追加学習を実施する |

- ポイントの数字は目安。関門ごとに実際の 95% の範囲の幅を出し、それより小さい差は決めない
- 測り方をそろえる(段 D0 で道具に足す): 同じ文書どうしの**対の比較**(差の 95% の範囲)・やり直しありの認識は **3 回の中央**(回ごとのぶれが大きいため)・時刻によらない CER を主に

### 3-3 編集前の定点を配信から取得する(段 D0-b。10-04 ユーザー決定「配信から自動で取得してよい」)
- ショートは編集後の音(BGM・効果音を足したものもある・詰めたカット)。ツールが普段文字起こしするのは編集前の切り抜きなので、**定点の主は編集前の音にする**
- 道具が、配信のアーカイブから 30〜40 秒の区間を取って `評価用_仮置き` に置く(yt-dlp の区間取得 = スタジオと同じ経路。置いたあとは今の流れ = まとめての文字起こし → 評価ドリル)
  - 量: **約 40 分(約 65 区間)**。メンバーが偏らないように・1 つの配信から 2 区間まで・声のある所を選ぶ(無音ばかりの区間は取り直す。少しは残す = 「何も話していない」も正解)
  - 選び方は乱数(seed で決まる)。盛り上がりの所だけに寄せない(普通の話し方も測る)。コラボ(重なり声)の配信も入れる
  - 配信の一覧の元: メンバーのチャンネル(名簿にチャンネルの情報が無いので、作るときに足す。公開の情報だけ)
  - 学習用のショートと同じ配信の同じ場面が入る心配: ショートの元の配信が分からないので完全には除けない。取る配信を**ショートの日付より新しいもの(2026-09 以降)**に限って避ける
- 定点の内訳: 編集前 約 40 分 + ショート 約 30 分。関門(3-2)は合計で数え、結果は 2 つを**分けても**出す(食い違いを見るため)
- 普段の校正(編集前の切り抜き)の時期で分けた測定も、今までどおり並べて見る(原則 3)

### D1 校正を速くする(今すぐ・データなしで作れる。効きめは使いながら測る)
- **D1-a 下書きを GPU で**: 学習用・仮置きのまとめての文字起こしを whisper.cpp(GPU。CPU の約 4 倍速い・精度は以前の測定で同じ)で作れるようにする。主のエンジンの決定(E1)とは別で、下書きを早く用意するため
- **D1-b 食い違いの印と候補**(第1版の段4-1 を前へ): 2 つ目のエンジン(候補: Qwen3-ASR 1.7B。GPU で 20 分の音声を約 30 秒・Whisper と間違え方が違う)でも認識し、文字の位置でそろえて、**食い違う所に印と「もう一方の候補」**を出す。1 押しで採れる。自動では書き換えない。
  - **定点(評価用)の文書には出さない**(正解が 2 つのエンジンに寄るのを避ける)。学習用と普段の文書だけ
  - 既定はオフで始め、「印の当たり率」(印の所を人が直した割合・人が直した所に印があった割合)を普段の校正から自動で測って、既定を決める
- ~~D1-c 焼き込みの字幕を読む実験(OCR)~~ **やめた(10-04 ユーザーの指摘)**: ショートの字幕は会話の全部を起こしていない・聞こえるままでもない(あくまで字幕)。下書きにすると抜けを書き足す手間が残り、言い換えにつられて正解が字幕の書き方に寄る。新しい依存も入れない

### E1 エンジンの決定(G1。第1版の段2-4 = マスタープランの I-1a)
- 比べるもの: faster-whisper large-v3(CPU・今)/ whisper.cpp large-v3(GPU)/ whisper.cpp large-v3-turbo(GPU。やり直しありでは未測定)/ Qwen3-ASR 1.7B(GPU)/ anime-whisper(ggml に変換できれば。できなければ外す)
- 測る前に、その時点の新しいモデルを 1 回調べる(09-27 の調査から時間がたつため)
- **クラウドの文字起こしとの比較を 1 回**(定点の音声を送る。上限の金額・送る先は**そのときユーザーと相談**。送る前に秒数と見積もり・キーは環境変数・結果は保存して再送しない)。
  ねらい: 手元のエンジンが最高水準とどれだけ離れているかを知り、あとの段にどこまで手間をかけるかを決める
- 決めること: 主のエンジン・2 つ目のエンジン(D1-b と E2 で使う)。精度の差が「分からない」なら、速さと間違え方(抜けが少ない方)で決める
- 決めたら: 入口の夜の自動の測定に「定点を認識し直す重い測定」を足す(GPU なら数分。推移を「調子」に出す)

### E2 抜けを減らす(G2。第1版の段3 = I-1b の前半)
- 「声があるのに行が無い」区間に印 → 2 つ目のエンジンで聞き直す(確かめ済みの定点は、すき間の抜けと幻覚をそのまま数えられるようになった = 10-04 夜の作り直し)
- ③-2「疑わしい所だけ認識し直す」が本物の音声で効くかも、ここで測る
- BGM の分離を声の検出に使う案は、ここまでで抜けが残ったときだけ(分離は入れない決定のまま)

### E3 名前の聞き違い(G2。第1版の段1 の続き = I-1b の後半)
- **ヒントのやり直し**: 語の一覧(hotwords)をやめて文の形のヒントだけ・語を減らす・やり直しを残す。先に学習用の文書で試し、定点で決める。主のエンジンが whisper.cpp になれば渡し方は prompt だけ
- **出る人に限った置き換え**(第1版の 1-3。未実装だった): 学習した「誤 → 正」を、その人が出る配信の文書だけに効かせる(一律の置換で普通の言葉を壊さない)
- D1-b の候補が名簿の呼び名と一致するときだけ自動で採る(第1版の 4-1 の決まり)は、当たり率を見てから
- 追加学習(FT)が先に採用されたら、ヒントは測り直してから(要らなくなる見込み)

### FT 追加学習(学習用 3 時間 + 採否は G3。新しい段)
- ねらい: ホロライブの名前・言い回し・配信の話し方を、モデルそのものに覚えさせる(置換もヒントも要らない所を増やす)
- やり方(案。始める前に、そのときの定番の方法を調べ直す): 主のエンジンのモデル(large-v3 か turbo)に LoRA(元のモデルを変えずに小さな差分だけ学習する方法)→ 差分を合わせる → 手元で動く形(whisper.cpp の ggml・faster-whisper の CTranslate2)に変換
- **学習と変換は借りた GPU の上だけ**(PC に PyTorch を入れない)。費用は 1 回 数百円の見込み(**始める前にユーザーと相談**)
- 守ること:
  - **評価用を絶対に入れない**(書き出しの道具が、評価用の印・評価用のフォルダ・定点の一覧の 3 つで機械的に検査する)
  - 学習用と検証用は配信の単位で分ける
  - **行の時刻つきで学習する**(時刻なしで学習すると、時刻の出力が崩れる)
  - 送るのは学習用の音声と校正だけ。終わったら借りた機械の中身を消す。キーは環境変数・リポジトリに入れない
- 採る条件: 定点で CER の差の 95% の範囲が改善の側・余分(幻覚)が増えない・名前の再現率が下がらない・**学習に入れていない人で悪化しない**・普段の校正の測定とも食い違わない。採らなくても、元のモデルに戻すのは設定で選ぶだけ
- 学習用が増えたら、やり直せる(同じ手順をスクリプトに残す)

## 6. やめること・閉じること
| 項目 | 理由 |
|---|---|
| Qwen3-ASR 0.6B(CPU) | 1.7B(GPU)より遅くて精度も低い。比較から外す |
| whisper.cpp の声の検出・Silero で声の無い所の行を捨てる | 測って悪化した(既定オフのまま。測り直さない) |
| 出る人の名前を語の一覧でヒントに渡す(今の `autoContext`) | 測って大きく悪化した。E3 で形を変えて試すまで既定オフ |
| 2 つの認識の多数決 | 日本語で伸びが小さい報告。食い違いは「印と候補」に使う |
| 焼き込みの字幕を読んで下書きにする(OCR。D1-c) | ショートの字幕は会話の全部ではなく、聞こえるままでもない(10-04 ユーザー)。下書き・学習の材料にしない |
| ローカルの LLM に候補を選ばせる(第1版の 4-2) | 後回し。D1-b の当たり率と FT の結果を見てから |
