## 0. 10-04 の見直し: 1台で始めて、2台に広げられる作り

### 0-1. なぜ1台でよいか
- ノート PC にした理由は「デスクトップ(13 世代)がよく落ちる」だけだった。CPU は i9-12900KF に替わり(13・14 世代の不安定の問題の外)、10-03 の入れ直しのあと Kernel-Power 41・予期しない終了・WHEA は 0 件(10-04 に確認。期間が短いので P1 の長時間テストで確かめる)
- 録画は作り直さない写し(`-c copy`)なので軽い(CPU 数%・書き込み 約 1MB/秒)。書き出し・文字起こしは今までどおり SLOTS で絞り、録画のプロセスの優先度を上げれば取り合わない
- 落ちて欠けても、P4(アーカイブで差し替え)で埋められる
- 1台で消えるもの: ノート PC の準備・LAN の公開とファイアウォール・2台の時計合わせ(NTP)・マークのバックアップの送り合い・有線 LAN とハブ

### 0-2. 2台に広げるための作りの決まり(P1 から守る)
- **録画は独立した部品 `recorder/`**(入口とは別のプロセス)。デスクトップで動かしても、ノート PC で動かしても同じプログラム・同じ HTTP API(4 の API)。
  1台のときは `127.0.0.1` だけで待ち受け、2台のときは LAN で待ち受ける(合言葉・Host の検査は最初から入れておく = 1台でも同じコードを通る)
- **入口・スタジオは「録画元の一覧」を通して読む**(設定 `recorders`: 名前・URL・合言葉。既定は手元の1つ)。ノート PC を足すときは一覧に1行足すだけで、スタジオのコードは変えない
- **スタジオは入口を通して再生する**(入口が `/live/...` を録画元へ中継する)。同じオリジンのまま CSP `script-src 'self'` と合言葉の決まりを守れ、CORS が要らない
- **時刻は各録画元の受信時刻(PDT)**。2台のときは、2つの録画のずれを時計だけに頼らず**音声の照合**で求める(P4 で作る照合の部品を使い回す)
- **書き出しの「取得」は録画元を選べる形にする**: 主の録画元 → 予備の録画元(2台のとき)→ アーカイブ(P4)の順で、欠けた所を埋める
- **録画の置き場所は設定**(C 以外のドライブを既定に勧める)。録画元ごとに空き容量を返し、入口の「調子」の画面に出す
- 録画の画質は選べる(1080p / 720p。容量を抑えたいとき。本番画質は P4 のアーカイブで出す)

### 0-3. 1台のときの注意
- 録画は入口と別のプロセスなので、入口の「すべて終了」→ start.bat の起動し直し(コードを直したあとなど)で録画は止まらない。録画の開始・停止は入口の画面から API で頼む
- 録画の部品はログインのあとに自動で起動する(スタートアップのショートカット。依頼の受付の「裏で起動」と同じ形。システムの設定は足さない)。落ちても起き直して新しいセッションを始める
- 優先度: 録画は「通常より上」、書き出し・文字起こしのジョブは「通常より下」
- 配信中に Windows Update で再起動させない(「アクティブ時間」の設定。ユーザーの作業)
- 1台では「配信の直後に非公開になったアーカイブ」の欠けは埋められない(2台なら片方が落ちても録画が続く)。これが P5 で2台にする主な理由の1つ

### 0-4. 2台にするとき(P5。容量が足りない・障害に備えたいときに)
- 容量: ノート PC が録画を持ち、デスクトップは書き出しに要るセグメントだけを取る(6 の「取得」)。デスクトップのディスクを録画で埋めない
- 障害: **二重録画**(同じ配信を両方で録る)。デスクトップが落ちてもノート PC の録画が続き、どちらかの欠けをもう一方で埋める。マークの正本はデスクトップ(fsync)+ ノート PC へ写し(5 のとおり)
- ノート PC の準備(09-28 の P0 の中身): OS の入れ直し・有線 LAN(ルーター経由。直結しない)・NTP・スリープなし・充電の上限・Windows Update の時間・ファイアウォールはプライベートだけ(4・9 のとおり)
- 録画の部品は NSSM でサービスにする(ログインなしで動く)か、スタートアップ。P5 を始めるときに決める

### 0-5. 書き出しは 30fps(10-04 の決定)

  AMF(GPU の作り直し)で速くするかは P2 で測ってから(画質の設定を通常の書き出しとそろえられる場合だけ)

### 0-9. P4: アーカイブで本番版に作り直す(2026-10-05 ユーザー決定)
決めたこと(ユーザー): 本番版は**速報版と入れ替える**(同じ名前・同じ場所。速報版は作業用フォルダに退避。文字起こし・カット・パックをそのまま使う)/

作り(境目。Claude が決めた):
- 単位は入口の書き出しのジョブ(`live/exports.json`。P3 から `studio {video, mark, start, end}` を持つ)。ジョブに `archive {state, label, message, progress, offset, residual, at, auto}` を足す。
  対象 = マークごとの最新のジョブで、`done`(入れ替え)か `error` + `needsArchive`(欠け。新しく作る)で、まだ `archive.state != done` のもの
- 時刻合わせ = **音の照合**。基準は速報版の mp4 そのもの(手元にあるので録画元に聞かない・録画を消したあとでもできる)。
  1. yt-dlp で `live_status`(`was_live` = 用意できた。`post_live`・`is_live` = まだ)・配信の開始時刻(`release_timestamp`)を取る
  2. 見当 = マークの絶対時刻 − 開始時刻。その前後の窓(最初は広く ±120 秒、2 本目からは前のずれの ±20 秒)のアーカイブの音だけを yt-dlp で取る
  3. 速報版の音(頭から最大 60 秒)と窓の音を相互相関(8kHz・モノラル。**numpy を使うので別プロセス** `home/live_align_worker.py`。入口のプロセスでは numpy を import しない決まり)→ アーカイブの秒と確かさ
  4. 欠けのマーク(速報版が無い)は、同じ録画の照合できたマークのずれを使う(いちばん近いもの。1 本も無ければできない)
- 取得と作り直し = スタジオのサーバーの YouTube の書き出しの中身を使う(二重に書かない): `POST /studio/api/live/section {videoId, start, end, path, volume, loudness, maxHeight, precision}` → ジョブ(`GET api/export?id=` で進み具合)。
  path は書き出し先の中の、まだ無い `.mp4`。音量は速報版と同じ扱い(`studio_audio()`)
- 検証と入れ替え: 30fps・長さ(±0.2 秒)・**速報版との音のずれが 1 コマ(0.034 秒)以内**(超えたら 1 回だけずれを足して作り直す。それでもだめなら入れ替えない)→
  速報版を `<配信のフォルダ>\作業用\速報版\` へ移し、本番版を元の名前へ(使用中で動かせなければ、あとでやり直す)→ `.clip.json` の `source.live.archive {videoId, start, end, offset, residual, at}`
- API(入口。オンのときだけ): `POST /live/api/archive {recorder, recording}`(対象の全部を始める。用意できていなければ 409 と文)・`POST /live/api/archive/cancel {recorder, recording}`・
  `GET /live/api/exports` の各ジョブの `archive` と、応答の `archiveInfo {ready, checkedAt, message}`
- 自動: 設定 `live.autoArchive`(既定オン)。録画が終わって 30 分後から、1 時間ごとにアーカイブの用意を確かめ(7 日でやめる)、用意できていて、ほかの重い処理が無いときに始める
- スタジオ: マークの `archived`(サーバーが持つ印。`path` と同じ扱い = 時刻を変えたら消える)。`POST /api/live/exported` に `archived: true`。
  画面: 終わった録画の帯に「アーカイブで作り直す」と進み具合・マークと書き出しの行に「本番版」の札・設定の「配信が終わったら自動で本番版に作り直す」
- できないもの: アーカイブが残らない・メンバー限定・非公開・配信者がアーカイブを切り貼りして音が合わない区間 → 速報版のまま(理由を出す)

録画を自動で消す(2026-10-05 ユーザー決定。**これまでの「自動では消さない」を変える**。設定 `live.autoDelete` 既定オン = Claude が足した止め方):
- **入れ替えが全部終わった録画はすぐ消す**: その録画の対象のマークが全部本番版に入れ替わったら、録画(`<置き場所>\<録画の id>\`)を消す。1 本でも作り直せなかったマークがあれば消さない

## 1. 概要
配信中にスタジオでマークして書き出し、配信終了直後に切り抜きを出せる状態にする。録画はノートPC(11世代i7)、編集はデスクトップで行う。

前提
- デスクトップは13世代CPUの問題でよく落ちる。録画はノートPCに置く。
- 後工程(編集ツールの文字起こし→カット→パック、cut2resolve、Resolve)は変更しない。今のスタジオと同じ書き出し設定で出して、そのまま流す。
- 録画はHLS(約4秒ごとの.tsファイル+再生リスト)で行う。録画しながらブラウザで再生・シークでき、落ちても失うのは最後の数秒で済む。

範囲
- 含む:ライブ録画、録画中の再生とマーク、録画待ち付きの書き出し、自動文字起こしへの接続、アーカイブ差し替え(P4)
- 含まない:新着配信の自動監視(保留中)、縦動画、メン限配信、YouTube以外

## 2. 全体構成
ノートPC(録画して配るだけ)
- 録画監視プロセス:streamlink+ffmpeg。切れたら再接続する
- HLSファイル:セッション別フォルダに保存する
- HTTPサーバー:LAN内だけで公開。再生リスト、録画状況、マークのバックアップ受付
- マークのバックアップ:デスクトップから送られたマークのコピー

デスクトップ(見てマークして書き出す)
- スタジオ(ブラウザ):hls.jsで再生し、今をマークする
- マークの正本:追記専用で、押すたびにディスクへ確定(fsync)する
- 書き出しジョブ:録画待ち→取得→書き出し→検証
- 編集ツール(既存のまま)

ネットワーク:2台ともルーターに有線でつなぐ(ポートが足りなければスイッチングハブを足す)。PC同士の直結はしない。直結するとノートPCのインターネット接続がWi-Fiになり、瞬断で録画が欠けるため。

## 3. 時刻モデル
マーク、書き出し区間、セグメントの位置は、すべて絶対時刻(UTC)で持つ。
- 基準:各セグメントに書き込まれる #EXT-X-PROGRAM-DATE-TIME(ノートPCが受信した時刻)
- マーク:hls.jsの playingDate で、再生中の場面の絶対時刻を取る
- 配信時刻(表示用):絶対時刻から配信開始時刻を引いて、表示するときだけ計算する
- ノートPCのNTP同期は必須。デスクトップの時計は使わない
- 既知のずれ:受信時刻なので、実際の配信より遅延分(数秒〜20秒程度)後ろになる。速報版では許容し、P4で音声照合により合わせる

配信開始時刻の取得(推奨案・未確定):次の順に試す
1. Holodexの実際の開始時刻(既存のHolodex取得処理で一緒に取る)
2. yt-dlpのメタデータ
3. 最初のセグメントの受信時刻

## 4. ノートPC側
OS:Windows 11を再インストールして容量を空ける。再インストール後にLANドライバーを確認する。

録画監視プロセス
- Pythonの常駐プロセスが、streamlinkとffmpegを子プロセスとして起動する。NSSMでWindowsサービスにする
- 最初から複数の配信を同時に録画できる作りにする(推奨案・未確定)

~~~
ffmpeg -hide_banner -i pipe:0 -c copy -f hls
  -hls_time 4 -hls_list_size 0 -hls_playlist_type event
  -hls_flags temp_file+program_date_time
  -hls_segment_filename session_002/seg_%06d.ts

フォルダ構成
~~~
recordings/<案件ID>/
  session_001/  index.m3u8, seg_000000.ts, ...
  session_002/  (再接続後の分)
  sessions.json
  marks-backup.jsonl
~~~

起動時の復旧
1. 前回のセッションに残った *.tmp を削除する
2. 読めない再生リストは「使えないセッション」と表示する
3. 前回のセッションを「中断」にして、新しいセッションを始める
- 管理ファイルは、一時ファイルに書いてからリネームで置き換える

終了と再起動の判定
- 配信が続いている:5秒→10秒→30秒と間隔を延ばしながら再起動する
- 配信が終わっている:#EXT-X-ENDLIST を付けて「終了」にする

HTTP API(LAN内のみ、トークン認証)
- POST /live/start :配信URLを受け取って録画を開始する(配信開始前でも、始まるまで待機する)
- POST /live/<ID>/stop :手動で停止する
- GET /live/<ID>/index.m3u8 :全セッションをつないだ再生リスト(Cache-Control: no-cache)
- GET /live/<ID>/<セッション>/<セグメント>.ts :セグメント本体
- GET /live/<ID>/status?since= :録画済みの最終時刻、終了したか、セグメント一覧、空き容量
- POST /live/<ID>/marks-backup :マークのバックアップ受付(同じIDは無視する)

容量管理:自動では消さない。状態画面に、録画ごとのサイズ、差し替え済みかどうか、空き容量を表示し、手動で消す。差し替え前の録画には「消すと救えない」印を付ける。

運用設定:充電上限80%程度、スリープなし、蓋は開けておく、配信中にWindows Updateで再起動させない、有線LAN

## 5. デスクトップ側:スタジオ
操作は今のまま(再生、シーク、今をマーク、①〜⑤、IN/OUT、書き出し)。違いは、動画の右端が伸び続けることだけ。配信はスタジオで見る。

~~~js
function markNow(kind) {
  const at = hls.playingDate;
  if (!at) return showError("再生位置の時刻を取得できません");
  return saveMark({ id: crypto.randomUUID(), at: at.toISOString(), kind });
}
~~~

マークの正本はデスクトップに置く
- 追記専用のJSONLかSQLite(WALモード)に保存し、押すたびにfsyncする
- 同じマークをノートPCへ非同期で送り、バックアップにする(LANが切れていたら後で送る)
- 起動時に正本とバックアップを比べ、正本のほうが少なければ知らせる

追加するUI:ライブに戻る、録画済み範囲と欠けの表示、録画待ち表示、接続状態、配信時刻の表示

## 6. 書き出しジョブ
SQLiteで管理する。書き出しと文字起こしは、それぞれ同時に1本まで。
1. 録画待ち:OUTの時刻より1セグメント先まで録画されるのを待つ(押した時点で予約する方式)
2. 取得:区間にかかるセグメントだけを取得する。欠けをまたぐ区間なら「要差し替え」にする
3. 書き出し:フレーム単位で正確に切り出し、今のスタジオと同じ設定で出す。~~エンコードはAMFを使い、フレームレートは固定60fpsにする~~(10-04: 30fps にそろえる。0-5)
4. 検証:ffprobeで確認する。失敗したら再試行し、通ったらリネームする
5. 完了:自動文字起こしへ渡す(配信中も走らせる)

~~~python
def segments_for(index, start, end):
    return [s for s in index if s.pdt < end and s.pdt + s.duration > start]
~~~

保存項目:ジョブID、案件ID、マークID、開始時刻、終了時刻、状態、試行回数、出力パス、最後のエラー。ジョブは冪等(何度やり直しても同じ結果)に作る。

## 7. 障害時の挙動
- デスクトップが落ちる:録画は無事。マークはfsync済みのもの+ノートPCのバックアップから戻せる。「実行中」のジョブは「待ち」に戻してやり直す
- 配信の切断・ネットの瞬断:再接続して新しいセッションを始める。欠けをまたぐ区間は「要差し替え」にする
- ノートPCの再起動:サービスとして自動で再開し、新しいセッションを始める
- LAN断:再生は止まるが録画は続く。マークはデスクトップに保存でき、バックアップは後で送る
- 容量不足:事前に警告する
- 配信直後の非公開化:差し替え前のライブ録画は消さない

## 8. 配信終了後とアーカイブ差し替え(P4、含める)
- 終了時は #EXT-X-ENDLIST を付ける。以後はアーカイブと同じ扱いにする
- 差し替え:アーカイブを取得し、音声照合でずれを補正して、同じマークで本番画質のものを再書き出しする。「要差し替え」の区間と、録画を始める前の頭の部分もここで救う

配信の頭の取得(推奨案・未確定):A+B
- A:配信開始前から録画を始めておく
- B:取れなかった頭の部分はP4で補う
- yt-dlp --live-from-start による並行取得はコストが高いので見送る
