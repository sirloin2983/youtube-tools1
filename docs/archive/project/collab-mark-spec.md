# コラボ動画のマーク転写機能 ― 設計案(v0)

ステータス: **実装済み(v0.1.7、実装順序案の (1)(2) まで。(3) 案Aの自動相関はまだ)**。「複数人のコラボで、一人のマークを他の配信の同じ部分にも転写する」機能について、時刻のズレをどう扱うかを中心に検討した。実装内容・設計からの変更点は末尾の「実装メモ(v0.1.6)」「追記(v0.1.7)」を参照。

## 課題

コラボでは複数人が同じ瞬間を体験していても、各自のVODでは録画開始タイミングがバラバラで同じ「秒数」を指さない。ズレは一定とは限らない: 配信中の回線遅延の変動、フレームレートの微小な違いによる累積ドリフト、途中の回線落ち・再接続、動画ごとに異なる広告/CM区切りなど。単純な定数オフセットでは長時間配信の末尾でズレる可能性がある。

設計は3つに分解できる: **①動画間の時刻対応(ズレ)をどう求めるか**、**②グループ化をどういうUIフローで行うか**、**③求めた対応関係を使ってマークをどう転写するか**。

## ①ズレの求め方(3案の比較)

### 案A: 音声どうしの相互相関(自動)
コラボは通話やゲーム音を互いに拾うため、音量エンベロープの相関でズレを推定できる可能性がある。既存の `analyze.estimate_lag`(音声×チャットの相関)を「音声×音声(別動画)」にそのまま流用できる。動画を前半・中盤・後半のような複数の窓に分けてそれぞれ推定し、窓ごとの推定ラグをロバスト回帰(一次関数 `t_ref = a * t_this + b`)に当てはめればドリフトにも対応できる。
- 長所: ユーザーの手間ゼロ。データが貯まれば精度も上がる。既存コードの流用が効き実装コストは中程度。
- 短所: 各自の声量バランスが極端に違ったり、BGMだけが強くて各自の声がほぼ乗らない配信だと相関が弱くなる、または無関係な区間を高相関と誤判定するリスクがある。既存の `LAG_MIN_CORR` / `LAG_MIN_CONTRAST` と同じ考え方の閾値で「自信がなければ推定しない」設計が必須。

### 案B: 手動アンカー点指定
両方の動画を見比べて「ここが同じ瞬間」を1〜2箇所指定してもらう。1点なら定数オフセット、2点あればドリフト(傾きa)も補正できる。
- 長所: 実装が軽く、精度が一番信頼できる。
- 短所: 毎回ユーザーの操作が要る。

### 案C: メタデータ(配信開始時刻)からの粗い推定
yt-dlpのupload_date等から大まかな差を出す。VOD録画開始と実配信開始にはズレがあるため分単位の精度しか出ない。案Aの探索範囲を絞る補助程度にしか使えない。

## 推奨(採用)
まず**案B(手動2点指定)だけを先に実装**して運用する。実装コストが低く、精度も一番信頼できる。「データが貯まってから高度な機能を足す」という既存の方針とも合う。案Aは、案Bの運用でズレの傾向・必要性が見えてきてから、`estimate_lag` の流用として低コストで追加できる段取りにしておく。

## ②グループ化のUIフロー(採用: 両方用意する)

グループを作るタイミングは2経路を両方用意する。

- **経路1: キュー追加時にまとめて選択(主経路)**。複数のURL/ファイルを一緒に登録するときに「コラボとしてまとめる」をONにすると、追加した動画がまとめて1グループになる。コラボ動画は同時に見つけて同時に登録することが多く、自然なタイミング。`batch.add()` は元々複数itemsを受け取れるので実装は軽い。
- **経路2: 動画一覧(確認画面)から後付けでグループ化**。すでに別々に登録・解析済みの動画を、一覧でチェックボックス選択して「コラボにまとめる」ボタンで後からグループ化する。経路1の弱点(後から気づいたケースに対応できない)を補う。グループ化のAPI自体は1つにして、呼び出し口を2箇所(キュー追加パネル/動画一覧)に置くだけでよい。

**グループ化とオフセット指定は別ステップ**にする。キュー追加時点(経路1)ではまだ解析前で動画を再生できないため、その場でアンカー点は指定できない。フローは:

1. 経路1 or 経路2 でグループを作る(この時点ではオフセット未設定)
2. 全員の解析が終わったら、動画一覧に「ズレ未設定」のようなバッジを表示
3. バッジから、2本を並べて再生できる画面を開き、案Bの手動アンカー点を指定する

自動検出(タイトル・概要欄の「〇〇さんとコラボ」等からグループを提案)は精度が低く過剰実装になりやすいため見送り。

## ③マーク転写のロジック

- グループ内の動画は基準動画に対して `t_ref = a * t_this + b` という一次関数(オフセット+微小な傾き)を持つ。傾き `a` はドリフト補正用で、アンカー点が1つしかない場合は `a = 1` 固定(定数オフセットのみ)。
- データ構造は最初から「区分的な複数の対応関数」を持てる配列にしておく(回線落ち区間や広告区切りの違いなど、一次関数1本でカバーしきれない区間に後で対応できるように)。最初の実装は要素1つでもよい。
- 転写のトリガーは**マークが採用(status=adopted)になったタイミング**とする(作成時や編集の都度ではない)。理由: ドラッグ調整中に何度も転写更新が走るのを避けられる。「採用=本当に良かった」という既存の判定記録の考え方とも一貫する。
- 転写先には新しい候補マークを作る。`src="collab"`、`collabFrom: {videoId, markId}` で由来を残す。**自動採用はしない**。同じ瞬間でも人によって「良い反応」かどうかは違うし、素の声・放送事故的な場面など転写してほしくない場合もあるため、既存の自動マークと同様、必ず人が採用/却下する候補どまりにする。
- 転写区間は元の区間より前後2〜3秒広げておく(音を聞いてからの反応タイミングは人によって数秒ズレるため)。あとは既存のドラッグ調整でそのまま微調整できる。
- **v0.1.7〜 転写先に既に(手動・自動・採用済みなど何でも)重なるマークがある場合は、新規候補を作らず既存のマークへ統合する**。詳細は下記「追記(v0.1.7)」。

## エッジケース・リスク

- 誰かが回線落ちして復帰した区間、動画ごとに異なる広告/CM区切りがある区間では、一次関数だけでは対応しきれない → 区分的な対応関数のデータ構造で後から対応できるようにしておく。
- 案Aの自動相関は、BGMだけが強くて各自の声がほぼ乗らない配信で誤判定するリスクがある → 閾値による「自信がなければ保留」を必須にする。
- 転写マークを見落として実質自動採用のような運用にしてしまうと、他人の配信のプライベートな反応を意図せず書き出すリスクがある → 候補どまりの原則を仕様として厳守する。
- グループから動画を外したときに、その動画由来の転写マークを残すか消すかを先に決めておく必要がある(既存の `store.delete` 同様、消さずに残す方が安全側)。

## 実装順序案

1. データモデルにグループとオフセット(a, b、区分的配列)を追加。グループ化UIは経路1(キュー追加時)・経路2(動画一覧から後付け)の両方を実装。オフセットは案B(手動2点指定)のみ。
2. 採用時のマーク転写ロジック(候補として作成、`src="collab"`)。
3. 運用してみて、案A(自動相関)を `estimate_lag` の流用で追加。

## 実装メモ(v0.1.6)

設計どおり実装できた点・実装時に決めた細部・設計から変えた点をまとめる。詳しい経緯は `claude/HANDOVER.md` のセッション4を参照。

**設計どおりの点**
- データモデル(グループ+区分的オフセット配列、`t_ref = a*t_this+b`)、案Bの手動2点アンカー、グループ化の経路1・経路2の両方、転写は採用時のみ発火・候補どまり・前後2〜3秒(実装値2.5秒)広げる、由来を `collabFrom` に残す — すべて設計どおり。

**実装時に決めた細部(設計に明記がなかった点)**
- 基準動画(base)は**グループ作成時に固定**し、後から変更する機能(rebase)は作っていない。基準の動画を外す・削除すると、そのグループごと削除する(残りのメンバーで基準を選び直す機能は無い)。エッジケース節の「グループから動画を外したときに転写マークを残すか」は設計どおり「残す」を採用したが、「基準を外したらどうするか」は設計時に未検討だったため、シンプルな「グループごと削除」を選んだ(下記「今後」参照)。
- 残りメンバーが1本になる場合も同様にグループごと削除(オフセットの相手がいなくなるため)。
- 1グループのメンバー上限は8本、グループ数の上限は50件(実装上の安全弁。根拠のある数字ではないので、狭ければ緩めてよい)。
- アンカー点の傾き(a)は 0.5〜1.5 倍の範囲外、2点の時刻差が20秒未満だとエラーにする(入力ミス対策。ドリフトは本来 a≒1 に極めて近いはずなので、実運用でここに引っかかるようなら閾値を見直す)。
- 「動画一覧に『ズレ未設定』のようなバッジを表示」は、③ 確認画面(review.js)ではなく新設の ④ コラボ画面(collab.js)に実装した。③ の動画選択プルダウンには簡易的に「・コラボ」という文字だけ付けている。

**設計時は想定していたが実装しなかった点**
- 「2本を並べて再生できる画面」(アンカー点を取るための同期プレーヤー)は作っていない。v0 はテキストで時刻を2つ入力するだけの簡易フォーム。実装コストと、既存の単一プレーヤー中心の review.js への影響を避けるための判断(詳しくはHANDOVER参照)。実用性を見て、次回以降で検討する。
- 案A(自動相関)は未着手のまま(設計どおり、案Bの運用を見てから)。

## 追記(v0.1.7): 転写先に既存マークがある場合の統合

**きっかけ**: 「コラボ動画のマーク機能ですでに同じような部分にマークがついてる場合は統合してほしい」とのユーザー要望。転写は前後2.5秒広げて候補を作る仕様だったため、相手側が既に自分で同じ瞬間をマーク(手動・自動候補・採用済みなど)していると、ほぼ同じ位置に重複した候補が並んでしまっていた。

**変更内容**(`store.py` の `_add_collab_candidate`):
- 転写しようとしている区間と、転写先の動画の**既存マーク(src・statusを問わない)**が少しでも重なっていたら、新規候補は作らず既存のマークへ統合する。
  - 重なりの判定は単純な区間の交差(`_overlaps`)。転写側は既に±2.5秒のマージンを持っているので、この緩い基準で十分と判断した。判定を厳しくしたい場合は `_overlaps` を調整すればよい。
  - 統合時は、**開始・終了を両方の区間を覆うように広げる**(狭める方向には動かさない)。判定(採用/不採用など)・ラベル・src は変えない。理由の欄にだけ転写元を追記する。
  - 例外: 統合対象が「書き出し済み」だった場合、範囲が実際に広がったときは既存の時刻編集ルールと同じく「採用」へ差し戻す(書き出し済みファイルは古い範囲のまま実体とずれるため)。範囲が変わらなければ書き出し済みのまま。
- 「既に同じ `from_vid`/`from_mark_id` からの転写を追加済み」の重複防止(既存の仕組み)はそのまま維持。統合はそれとは別に、**転写元が違っても位置が重なっていれば**働く。

**トレードオフ・残課題**
- 区間の交差だけを基準にしているので、たまたま近いが本当は別の反応だった場合にも統合されてしまう可能性はある(偽陽性)。見落として重複候補が残るより安全側という判断で、今のところ許容している。運用してみて頻発するようなら、重なりの割合(IoU)や中心時刻の距離など、もう少し厳密な基準に変えることを検討する。
- 統合時に足す理由の重複防止は文字列(転写元のタイトル)の単純比較。動画タイトルを後から変えると同じ転写元からの2件目が別メモとして追記されうるが、実害はなく表示が少し増えるだけ。

このタイミングで、切り抜きスタジオ本体の書き出し機能にも「書き出しの音量調整(既定75%)」を追加した(コラボとは別件。詳細は `claude/clip-studio-spec.md` の設計判断を参照)。あわせて v0.1.7 とした。
