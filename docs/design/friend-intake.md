> **状態(2026-10-04): 実装済み(ホーム 0.26.0・送るアプリ 2.0.0。2-7 の「編集」から手で届けるを足した)**。1.2.0 の時点で実機の通しは確認済み(友人のアプリから送った動画が受け付けられて動いた)。2-6(時間の指定・カット・重み)は本物の YouTube・Dropbox ではまだ。

## 1. 目的
友人から「切り抜いてほしい配信」「友人が切り抜いた動画」を受け取り、PC で**自動で文字起こしまで**流す。
校正・カット・パックはこれまでどおりユーザーが「編集」で行う。

## 2. 決めたこと(2026-09-30 ユーザー)
| 項目 | 決定 |
|---|---|
| 依頼の種類 | ① 配信の URL(YouTube)② 友人が切り抜いた動画ファイル |
| 受け取りの経路 | ユーザーの Dropbox(有料 2TB)。友人はお金もアカウントも要らない |
| 友人の操作 | 友人の PC に小さなプログラム(C#。何も入れずに動く)を渡し、「送る」を押すだけにする |
| 送り方 | **A. Dropbox の API で直接アップロード**(アプリ専用のフォルダだけに書ける鍵)。ファイルリクエストのリンクは予備として使える |
| URL の依頼の処理 | 解析 → 自動マークの上位 N 個を採用 → 書き出し → 文字起こし(パックはしない)。N は依頼ごと(1〜10・既定 3) |
| 動画の依頼の処理 | 作業データへコピー → 文字起こし |
| 実行 | 届いたらすぐ自動で流す(ホームでの承認は要らない) |
| 友人への知らせ | しない。友人のプログラムに出すのは「送りました ✓」まで |
| 配信者(字幕の色) | 動画: 友人のプログラムで選ぶ(任意)/ URL: チャンネル名から自動(今の「まとめて実行」と同じ) |
| メモ | 書ける。自動の処理には使わず、ホームで読むだけ |
| PC が止まっていた間の依頼 | 次にホームを起動したときに流す |

## 2-2. 友人が選ぶ形(2026-10-01 ユーザー決定・ホーム 0.16.0・送るアプリ 1.1.0)
友人は送るたびに、PC でどこまで進めるかを選ぶ(アプリの既定は ①。前回の選択は覚えない)。JSON の `flow`。

| 表示名 | flow | 配信の URL | 友人の動画 |
|---|---|---|---|
| ① 全自動(パックまで作って届ける) | auto | 解析 → 上位 N 個 → 書き出し → 文字起こし → パック → 出力\ へ | 文字起こし → パック → 出力\ へ |
| ② 軽く確認(文字起こしまで) | check | 解析 → 上位 N 個 → 書き出し → 文字起こし | 文字起こし |
| ③ 全部人が行う(解析まで) | manual | 解析だけ(切り抜く所はスタジオで人が決める) | スタジオに入れて解析だけ |

- `flow` の無い依頼(1.0.0 のアプリ・手で置いたファイル)と知らない値は ②
- ① のパックは字幕の校正の前のもの。パックのフォルダを zip にして、見張るフォルダの `出力\<依頼 id>__<名前>.zip` に置く
  (zip は Dropbox の外 = パックの隣で作ってから移す。書きかけを同期させない)。止まったら `出力\<依頼 id>__<題名>.失敗.txt` に理由
- 友人のアプリの「受け取る」が `/出力/` を一覧にしてダウンロードする。そのため鍵に読みの権限(files.content.read・files.metadata.read)を足した。
  読めるのはアプリ専用のフォルダの中だけ。1.0.0 の鍵は作り直して zip を渡し直す
- (2-3 で変更)Dropbox から消すのは友人のアプリだけ(受け取って確かめたあと)。PC は消さない

### 2-4. 話す人(2026-10-01 ユーザー。ホーム 0.18.0・編集 0.28.0・送るアプリ 1.3.0)
- 友人が人数(1〜10)と名前を入れると、JSON の `speakers` {"count", "names"}。PC はこの実行で文字起こしした文書だけ、文字起こしのあとに段「話者分離」
  (編集の /api/diarize に numSpeakers と names)。1人なら判別せず全部の行をその人に。2人以上は覚えている声と名前の一覧だけで照らし合わせ、1人ずつ残れば消去法
- 名前の分からない人は「話者1」などのまま。失敗しても依頼は止めない(一部失敗)。① 全自動ではパックの前なので、字幕の色は付いた名前で決まる
- 「編集」の話者判別の人数にも「1人」を足した

### 2-6. 時間の指定・カット・解析の重み・同じ配信の送り直し(2026-10-02 ユーザー。ホーム 0.23.0・スタジオ 0.14.0・送るアプリ 2.0.0)
設計と聞き取りの記録: `.design/request-sender-overhaul/DESIGN_BRIEF.md`(送るアプリの画面の全面見直しも同じ文書)。
- **区間**: 友人が配信ごとに「切り抜く数」(`items[].top`。1〜10・配信ごと)と区間(`items[].ranges` = [{"start": 秒, "end": 秒}]。0〜10 個・1つ 60 分まで)を入れる。
  **区間が切り抜く数に足りない分だけ、自動の見どころで埋める**(指定 1・数 3 なら 自動 2)。区間が数以上なら解析しない(その区間だけを yt-dlp で取る)。
  ③(manual)では区間を書かない・PC も使わない(ユーザー「③ + 時間指定はやらない」)
- **前後の余白**: PC が自動で 2 秒ずつ足す(`autorun.RANGE_PAD`・`pad_range`。0 と配信の長さで切る。友人には選ばせない)
- PC: `intake.parse_ranges`(形が違う区間だけ断って理由を知らせる。配信の長さより後の区間は断り、終わりは長さで切る)→ `autorun.start_request` の items の `ranges`
  → 段「採用」が スタジオの `POST /api/video/request-marks`(区間を採用済みの手動マークに・自動の上位(区間と重ならない)を足りない分だけ採用・使い回す)
  → その実行は、その区間と自動の分だけを扱う(`run.marks`)
- **カット**: `cut` = "none" / "silence"(① のときだけ。動画・URL の両方)。`intake.parse_cut` → `Run.cut` → パックのカットの方法。無ければホームの設定 `autorun.cut`
- **解析の重み**: `weights` = {"audio", "chat", "comments"}(0〜3。URL の依頼で、友人が「重みを指定する」を入れたときだけ)。`intake.parse_weights` → スタジオの解析の設定の
  wAudio・wChat・wComments(ほかの設定はスタジオのまま)。解析済みで重みが同じなら使い回し、違えば解析し直す(`autorun._weights_differ`。取り込み済みの音量・チャットは使い回される)
- **同じ配信の送り直し**: 断らない(ユーザー「同じ配信でも受け付けるが解析結果などは流用する」)。解析・書き出した切り抜き・文字起こしは使い回す。
  ① はパックを今回の設定(カット・映像トラック)で作り直して届ける(`Run.overwrite`)。1つの依頼に同じ配信を2回書いたら1回だけ
- 送るアプリ 2.0.0 は 1.4.0 までの PC にも送れる(知らないキーは捨てられ、今までどおり自動で N 個)。逆に 1.4.0 までのアプリの依頼も今までどおり動く

### 2-7. 「編集」から手で友人へ届ける(2026-10-04 ユーザー「友人へ届けるボタン作って」。ホーム 0.26.0・編集 0.42.0。送るアプリは変えない)
- 「編集」の ③ パックの「前回のパック」に「友人へ届ける」(入口から開いたときだけ)。校正したあとのパックなど、① 全自動以外のパックを友人へ渡すため
- 入口の画面の共通の API `api/ytt/deliver`(`{op: "start", dir, title}` → 裏の仕事 / `{op: "status", job}`)。作り方は `home/deliver.py` の `zip_pack` の1か所(① 全自動の `autorun._deliver_one` も同じもの)
- 名前は `出力\<YYYYMMDD-HHMMSS-xxxxxx>__<文書の題名>.zip`(送るアプリの `OutputFolder.NameRx` と同じ形 → アプリは題名だけを出す)。同じ名前があれば末尾に4文字
- 送れるのは cut2resolve が作ったパックのフォルダだけ(`txindex.is_pack_dir`。画面から任意のフォルダを Dropbox へ出させない)。受付のフォルダが決まっていない・見つからなければ断る
- 外へ出す操作なので、押したら確認を出す(作ったあとにカット・字幕が変わっていれば、その注意も)。zip は裏で作り、画面は1秒ごとに状態を聞く。同時に作るのは1本
- zip は動画を圧縮しない(ZIP_STORED)ので CPU はほとんど使わない → 重い処理の枠(`jobs.SLOTS`)は通さない(文字起こしの後ろで待たせない)
- 送るアプリの一覧の説明は「字幕は校正の前」のまま(アプリは変えていない)。校正済みかは題名で伝える

### 2-8. 配信者をまとめる・プルダウン・字幕の色(2026-10-05 ユーザー。ホーム 0.34.0・編集 0.55.0・cut2resolve 0.21.0・送るアプリ 2.1.0)
決めたことと将来の形(フォントなどを足すときの決まり)は `docs/plan/sender-streamer-color-plan.md`。
- 送るアプリ: 「配信者」(動画のときだけの 1 つの欄)と「話す人」を **「配信者」の 1 種類**にまとめた(URL・動画の両方で人数分)。1 行 = 名前(プルダウン。一覧に無い名前も打てる)+ 色(6 桁のカラーコード・# なし)。
  色だけで名前が空・色が 6 桁でない行は、送る前に止める。人数だけ(名前なし)の指定は残した
- JSON: `speakers` に `people` = [{"name", "style": {"color": "RRGGBB"}}](名前のある行だけ・色を入れた行だけ `style`)。`names` は今までどおり書く。`streamer` = 1 人目の名前(**URL の依頼にも付く**)
- PC: `intake.parse_speakers` が `styles` = {名前: {"color": "#RRGGBB"}}(鍵ごとの許可の一覧 `STYLE_KEYS`。`names` に入っている名前だけ・知らない鍵は捨てる)→ `autorun` の話者分離の段のあと、
  文書ごとに編集の `POST api/speakers/sub`(文書の話者の `sub.color` = その文書にだけ覚える。PC の「自分の色」には登録しない)→ パックの要求に `output.speakerStyles`。
  色の決まり方: 指定の色 → メンバーカラー → 配信者の色 → 黒。色を覚えられなくても・パックの側が古くても依頼は止めない
- URL の依頼の `streamer`: メンバーと合えば、チャンネル名からの自動(`_auto_streamer`)より優先。合わない・無い → 今までどおり
- 受付の一覧: 「配信者: n人(…)・色の指定 n人」、字幕の色の元の人は「字幕の色: 名前」
- 2.1.0 のアプリは 0.33.0 までの PC にも送れる(知らないキーは捨てられる)。2.0.0 までのアプリの依頼も今までどおり

### 2-9. 区間だけの依頼をあとから解析する・友人の区間の長さを使う(2026-10-05 ユーザー。ホーム 0.35.0。送るアプリは変えない)
- 背景: 区間が切り抜く数に足りている依頼は解析しない(2-6)。友人の区間は「自動の候補を見ずに人が選んだ見どころ」= 検出の見逃しを測れる唯一の正解だが、解析しないので比べる相手が無かった
- **あとから解析**(ユーザー「依頼のパック化まで終わったあとに解析して、自動の候補と比べる。タイミングは夜ではなく、現時点の依頼が全部終わったとき」): `autorun` の mode `post_analyze`(段は analyze だけ・「あとから解析(測るため)」)。
  一覧 `logs/autorun-deferred.json`(配信の ID ごと・14 日・3 回)・待ちが無くなって `DEFER_IDLE_SEC`(60 秒)後に 1 本ずつ・新しい実行が入ったらやめて一覧に戻す(スタジオの `api/queue/cancel`)・
  以前の依頼の取り込み(実行の記録から 1 回・30 日以内・20 本)・`YTT_DEFER_ANALYZE=off`。友人へ届けない・受付の記録を変えない・1 日の上限に数えない・「調子」の失敗に数えない。
  依頼の区間のマーク(手動・採用済み)は `store.replace_auto` が残す(テストで固定)
- **測る**: `dev/eval_marks.py` の `friendRanges`(友人の区間ごとに、自動の候補が当たったか・順位・上位 5/10/20 で拾えた率・見逃しの近くの候補・点数の内訳・長さごと。未解析の配信は別に数える)。
  区間の出どころは実行の記録の `ranges`(余白 `RANGE_PAD` の前)。今までの採用率には入れない(自動で埋めた分 `adoptedBy: auto` は今までどおり数えない)。**重みは自動では変えない**(数字を見て決める)
- **長さ**(ユーザー「区間の長さのデータも取っておいて、自動のときに適切な長さを使う」): `eval_marks` の `clipLength`(人が選んだ長さ = friend・manual・adjusted・kept と、山の位置・目安 `suggest`)。
  **仮の決定**: 使うのは友人の依頼の足りない分を埋める解析だけ(`autorun._friend_length`。友人の区間 20 個・配信 5 本から。長さ = 中央値を 10〜120 秒に・山の前の割合は見本 10 個から)。
  理由: 10-05 の時点で友人の区間は 4 個・中央値 約 150 秒で、スタジオの既定 45 秒(ショート向け)の 3 倍以上 = 性質が違うので、ユーザー自身のまとめて実行・スタジオの解析には効かせない。
  目安は全体で 1 つの固定の長さ(場面ごとに長さを変えるには検出の仕組みの変更が要る。分布を見てから)
- 変わったふるまい: まとめて実行の中止で、その実行が入れたスタジオの解析も取り消す(今までは解析だけ動き続けた)

## 3. 全体の流れ
```
友人の PC                          ユーザーの Dropbox(2TB)                  ユーザーの PC
依頼ボックス.exe ─API でアップロード→ /アプリ/切り抜き依頼/ ─同期→ Dropbox\アプリ\切り抜き依頼\
 (動画をドラッグ / URL を貼る)                                               │ ホーム(home/intake.py)が 30 秒ごとに見る
                                                                              ▼
                                                             検査 → まとめて実行(home/autorun.py)→ 文字起こし
                                                             元のファイルは 受付済み\日付\ へ(消さない)・断ったら 失敗\ へ + 理由
```
- PC から取りに行く形(ホームのポートを外に開けない)。1つの画面の XSS で全ツールの API が使える構造なので、外からの接続は受けない(AGENTS.md の【高】)
- 予備: ブラウザの Dropbox ファイルリクエスト(保存先を同じフォルダに)。友人のプログラムが動かないときに使う。容量は受け取る側(ユーザー)だけに数えられる

## 4. 友人のプログラム(依頼ボックス)
- C# 5・WinForms。Windows に入っている .NET Framework 4 の csc で作る(ホロカラーと同じ `build.bat` の形)。置き場所は `request-sender/`(仮)
- 画面: 動画のドラッグの欄 / 配信の URL(複数可)と切り抜く数(1〜10)/ 配信者(任意。メンバーの一覧 `holo-colors/members.json` から選ぶ)/ メモ / 「送る」/ 進み具合と「送りました ✓」
- 右クリックの「送る」メニューにも出す(`shell:sendto` にショートカットを置く。最初の起動で聞く)
- 送る前に確かめる(便利のため。本当の検査は PC 側): URL が YouTube か・動画の拡張子・数の範囲
- 送るもの: 動画があれば先に動画、**最後に依頼の JSON**(下の 5)。JSON が届いた = そろった、の合図にする(同期の途中のファイルを読まないため)
- Dropbox の API:
  - アプリは「App folder」の権限だけ(`/アプリ/切り抜き依頼/` の外は読めない・書けない)。スコープは `files.content.write` だけ(読みは要らない)
  - 鍵: PKCE で一度だけ承認して得た refresh token + app key(secret は使わない)。exe には焼き込まず、隣の `config.json` に置く
  - 150MB 以下は `files/upload`、それより大きい動画は `upload_session/start → append_v2 → finish`(8MB ずつ・失敗した塊だけやり直す)
  - 名前がぶつかったら `autorename`。`Dropbox-API-Arg` のヘッダーの JSON は ASCII 以外を `\uXXXX` にする(日本語のファイル名で必要)
  - .NET Framework では TLS 1.2 を明示する(`ServicePointManager.SecurityProtocol`)
- 鍵を作る手順はユーザーの PC の補助スクリプト(`dev/` に Python。仮)で行い、できた `config.json` を exe と一緒に友人へ渡す
- **鍵をリポジトリに入れない**(Public)。`config.json` は `.gitignore`、`dev/push_helper.py` の検査に Dropbox の鍵の形を足す

## 5. 依頼の形
### 5-1. 依頼の JSON(友人のプログラムが作る。`<日時>-<乱数>.request.json`)
```json
{"v": 1, "kind": "video", "files": ["<日時>-<乱数>__にぇの叫び.mp4"], "streamer": "さくらみこ", "memo": "", "sentAt": "2026-10-01T12:00:00+09:00"}
{"v": 1, "kind": "url", "items": [{"url": "https://www.youtube.com/watch?v=xxxxxxxxxxx", "top": 5}], "memo": "", "sentAt": "…"}
```
- 2.1.0 から(2-8): `"speakers": {"count": 2, "names": ["A", "B"], "people": [{"name": "A", "style": {"color": "FF00AA"}}, {"name": "B"}]}`・URL の依頼にも `"streamer": "A"`

## 7. 安全
- 鍵(または予備のリンク)を知る人は誰でも依頼を入れられ、自動で流れる。対策:
  - 鍵はアプリ専用のフォルダだけ。漏れたら Dropbox の設定でアプリの接続を切れば無効(新しい鍵を渡し直す)
  - 上限で PC を長く占有させない(仮の値: 1日 5 件・配信 8 時間まで・動画 1 本 20GB まで。設定で変えられる)
  - 送り主の名前・依頼の中身は本人の証明にならない。受け付けの判断には使わない
- 受け付ける URL は youtube.com / youtu.be の配信・動画だけ(11 文字の ID を取り出して、それだけを渡す。任意の URL を yt-dlp に渡さない)
- 他人が作った動画を ffmpeg で読むこと自体が攻撃の入口になり得る: 拡張子と ffprobe で形を確かめてから先へ。ffmpeg は新しく保つ
- JSON・テキストは大きさの上限(例 64KB)を付けて読み、知らないキーは捨てる。パスは見張るフォルダの中だけ(`..`・絶対パス・ネットワークのパスを断る。`fsio.is_network_path`)
- 見張るフォルダにネットワークドライブは選べない(段2 の「動画を選び直す」と同じ規則)
