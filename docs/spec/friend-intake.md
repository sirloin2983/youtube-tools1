# 友人からの依頼の受付(設計)

> **状態(2026-10-08): 実装済み(ホーム 0.45.2・送るアプリ 2.5.1)**。1.2.0 の時点で実機の通しは確認済み(友人のアプリから送った動画が受け付けられて動いた)。2-6(時間の指定・カット・重み)・2-8(配信者・色)は本物の YouTube・Dropbox ではまだ。
> **実際の Dropbox で未確認**: URL の依頼・150MB 超の動画・受け取り後の削除(files/delete_v2。日本語名も)・ダウンロードの続き(Range)・権限不足のエラー・content_hash(友人に 2.1.0 の zip を渡して 1 本通すときに確かめる。一覧は `plan/user-tasks.md`)。
> 実装は `src/home/intake.py`・`src/home/autorun.py`・`friend-apps/request-sender/`(WORKLOG の 2026-09-30〜10-05)。この文書は**今の仕様**(2026-10-07 に `docs/design/` から移した)。
> 方針(ユーザー): 「全部これでよい。問題があれば追加する」。下の「仮の値」は動かしてみて直す。

## 1. 目的
友人から「切り抜いてほしい配信」「友人が切り抜いた動画」を受け取り、PC で**自動で文字起こしまで**流す。
校正・カット・パックはこれまでどおりユーザーが「編集」で行う。

## 2. 決めたこと(2026-09-30 ユーザー)
| 項目 | 決定 |
|---|---|
| 依頼の種類 | ① 配信の URL(YouTube)② 友人が切り抜いた動画ファイル |
| 受け取りの経路 | ユーザーの Dropbox(有料 2TB)。友人はお金もアカウントも要らない |
| 友人の操作 | 友人の PC に小さなプログラム(C#。何も入れずに動く)を渡し、「送る」を押すだけにする |
| 送り方 | **A. Dropbox の API で直接アップロード**(アプリ専用のフォルダだけに書ける鍵)。ファイルリクエストのリンクは予備として使える |
| URL の依頼の処理 | 解析 → 自動マークの上位 N 個を採用 → 書き出し → 文字起こし(パックはしない)。N は依頼ごと(1〜10・既定 3) |
| 動画の依頼の処理 | 作業データへコピー → 文字起こし |
| 実行 | 届いたらすぐ自動で流す(ホームでの承認は要らない) |
| 友人への知らせ | **知らせる(2026-10-01 ユーザー決定。当初の「しない」を変えた)**。① 全自動のパックと、処理が止まったときの理由(`.失敗.txt`)を Dropbox の `出力\` に置き、友人のアプリの「受け取る」が一覧・ダウンロードする(2-2・2-3・9)。送ったあとのアプリには「送りました ✓」 |
| 配信者(字幕の色) | 動画: 友人のプログラムで選ぶ(任意)/ URL: チャンネル名から自動(今の「まとめて実行」と同じ) |
| メモ | 書ける。自動の処理には使わず、ホームで読むだけ |
| PC が止まっていた間の依頼 | 次にホームを起動したときに流す |

## 2-2. 友人が選ぶ形(2026-10-01 ユーザー決定・ホーム 0.16.0・送るアプリ 1.1.0)
友人は送るたびに、PC でどこまで進めるかを選ぶ(アプリの既定は ①。前回の選択は覚えない)。JSON の `flow`。

| 表示名 | flow | 配信の URL | 友人の動画 |
|---|---|---|---|
| ① 全自動(パックまで作って届ける) | auto | 解析 → 上位 N 個 → 書き出し → 文字起こし → パック → 出力\ へ | 文字起こし → パック → 出力\ へ |
| ② 軽く確認(文字起こしまで) | check | 解析 → 上位 N 個 → 書き出し → 文字起こし | 文字起こし |
| ③ 全部人が行う(解析まで) | manual | 解析だけ(切り抜く所はスタジオで人が決める) | スタジオに入れて解析だけ |

- `flow` の無い依頼(1.0.0 のアプリ・手で置いたファイル)と知らない値は ②
- ① のパックは字幕の校正の前のもの。パックのフォルダを zip にして、見張るフォルダの `出力\<依頼 id>__<名前>.zip` に置く
  (zip は Dropbox の外 = パックの隣で作ってから移す。書きかけを同期させない)。止まったら `出力\<依頼 id>__<題名>.失敗.txt` に理由
- 友人のアプリの「受け取る」が `/出力/` を一覧にしてダウンロードする。そのため鍵に読みの権限(files.content.read・files.metadata.read)を足した。
  読めるのはアプリ専用のフォルダの中だけ。1.0.0 の鍵は作り直して zip を渡し直す
- (2-3 で変更)Dropbox から消すのは友人のアプリだけ(受け取って確かめたあと)。PC は消さない

### 2-4. 話す人(2026-10-01 ユーザー。ホーム 0.18.0・編集 0.28.0・送るアプリ 1.3.0)
- 友人が人数(1〜10)と名前を入れると、JSON の `speakers` {"count", "names"}。PC はこの実行で文字起こしした文書だけ、文字起こしのあとに段「話者分離」

### 2-6. 時間の指定・カット・解析の重み・同じ配信の送り直し(2026-10-02 ユーザー。ホーム 0.23.0・スタジオ 0.14.0・送るアプリ 2.0.0)
送るアプリの画面の全面見直しで決まったことは 2-10。
- **区間**: 友人が配信ごとに「切り抜く数」(`items[].top`。1〜10・配信ごと)と区間(`items[].ranges` = [{"start": 秒, "end": 秒}]。0〜10 個・1つ 60 分まで)を入れる。
  **区間が切り抜く数に足りない分だけ、自動の見どころで埋める**(指定 1・数 3 なら 自動 2)。区間が数以上なら解析しない(その区間だけを yt-dlp で取る)。
  ③(manual)では区間を書かない・PC も使わない(ユーザー「③ + 時間指定はやらない」)
- **前後の余白**: PC が自動で 2 秒ずつ足す(`autorun.RANGE_PAD`・`pad_range`。0 と配信の長さで切る。友人には選ばせない)
- PC: `intake.parse_ranges`(形が違う区間だけ断って理由を知らせる。配信の長さより後の区間は断り、終わりは長さで切る)→ `autorun.start_request` の items の `ranges`
  → 段「採用」が スタジオの `POST /api/video/request-marks`(区間を採用済みの手動マークに・自動の上位(区間と重ならない)を足りない分だけ採用・使い回す)
  → その実行は、その区間と自動の分だけを扱う(`run.marks`)
- **カット**: `cut` = "none" / "silence"(① のときだけ。動画・URL の両方)。`intake.parse_cut` → `Run.cut` → パックのカットの方法。無ければホームの設定 `autorun.cut`
- **解析の重み**: `weights` = {"audio", "chat", "comments"}(0〜3。URL の依頼で、友人が「重みを指定する」を入れたときだけ)。`intake.parse_weights` → スタジオの解析の設定の
  wAudio・wChat・wComments(ほかの設定はスタジオのまま)。解析済みで重みが同じなら使い回し、違えば解析し直す(`autorun._weights_differ`。取り込み済みの音量・チャットは使い回される)
- **同じ配信の送り直し**: 断らない(ユーザー「同じ配信でも受け付けるが解析結果などは流用する」)。解析・書き出した切り抜き・文字起こしは使い回す。
  ① はパックを今回の設定(カット・映像トラック)で作り直して届ける(`Run.overwrite`)。1つの依頼に同じ配信を2回書いたら1回だけ
- 送るアプリ 2.0.0 は 1.4.0 までの PC にも送れる(知らないキーは捨てられ、今までどおり自動で N 個)。逆に 1.4.0 までのアプリの依頼も今までどおり動く

### 2-7. 「編集」から手で友人へ届ける(2026-10-04 ユーザー「友人へ届けるボタン作って」。ホーム 0.26.0・編集 0.42.0。送るアプリは変えない)
- 「編集」の ③ パックの「前回のパック」に「友人へ届ける」(入口から開いたときだけ)。校正したあとのパックなど、① 全自動以外のパックを友人へ渡すため
- 入口の画面の共通の API `api/ytt/deliver`(`{op: "start", dir, title}` → 裏の仕事 / `{op: "status", job}`)。作り方は `src/home/deliver.py` の `zip_pack` の1か所(① 全自動の `autorun._deliver_one` も同じもの)
- 名前は `出力\<YYYYMMDD-HHMMSS-xxxxxx>__<文書の題名>.zip`(送るアプリの `OutputFolder.NameRx` と同じ形 → アプリは題名だけを出す)。同じ名前があれば末尾に4文字
- 送れるのは cut2resolve が作ったパックのフォルダだけ(`txindex.is_pack_dir`。画面から任意のフォルダを Dropbox へ出させない)。受付のフォルダが決まっていない・見つからなければ断る
- 外へ出す操作なので、押したら確認を出す(作ったあとにカット・字幕が変わっていれば、その注意も)。zip は裏で作り、画面は1秒ごとに状態を聞く。同時に作るのは1本
- zip は動画を圧縮しない(ZIP_STORED)ので CPU はほとんど使わない → 重い処理の枠(`jobs.SLOTS`)は通さない(文字起こしの後ろで待たせない)
- 送るアプリの一覧の説明は「字幕は校正の前」のまま(アプリは変えていない)。校正済みかは題名で伝える

### 2-8. 配信者をまとめる・プルダウン・字幕の色(2026-10-05 ユーザー。ホーム 0.34.0・編集 0.55.0・cut2resolve 0.21.0・送るアプリ 2.1.0)

### 2-9. 区間だけの依頼をあとから解析する・友人の区間の長さを使う(2026-10-05 ユーザー。ホーム 0.35.0。送るアプリは変えない)
- 背景: 区間が切り抜く数に足りている依頼は解析しない(2-6)。友人の区間は「自動の候補を見ずに人が選んだ見どころ」= 検出の見逃しを測れる唯一の正解だが、解析しないので比べる相手が無かった
- **あとから解析**(ユーザー「依頼のパック化まで終わったあとに解析して、自動の候補と比べる。タイミングは夜ではなく、現時点の依頼が全部終わったとき」): `autorun` の mode `post_analyze`(段は analyze だけ・「あとから解析(測るため)」)。
  一覧 `logs/autorun-deferred.json`(配信の ID ごと・3 日(10-07 に 14 → 3)・3 回)・待ちが無くなって `DEFER_IDLE_SEC`(60 秒)後に 1 本ずつ・新しい実行が入ったらやめて一覧に戻す(スタジオの `api/queue/cancel`)・
  以前の依頼の取り込み(実行の記録から 1 回・30 日以内・20 本)・`YTT_DEFER_ANALYZE=off`。友人へ届けない・受付の記録を変えない・今日の件数に数えない・「調子」の失敗に数えない。
  依頼の区間のマーク(手動・採用済み)は `store.replace_auto` が残す(テストで固定)
- **測る**: `dev/eval_marks.py` の `friendRanges`(友人の区間ごとに、自動の候補が当たったか・順位・上位 5/10/20 で拾えた率・見逃しの近くの候補・点数の内訳・長さごと。未解析の配信は別に数える)。
  区間の出どころは実行の記録の `ranges`(余白 `RANGE_PAD` の前)。今までの採用率には入れない(自動で埋めた分 `adoptedBy: auto` は今までどおり数えない)。**重みは自動では変えない**(数字を見て決める)
- **長さ**(ユーザー「区間の長さのデータも取っておいて、自動のときに適切な長さを使う」): `eval_marks` の `clipLength`(人が選んだ長さ = friend・manual・adjusted・kept と、山の位置・目安 `suggest`)。
  **仮の決定**: 使うのは友人の依頼の足りない分を埋める解析だけ(`autorun._friend_length`。友人の区間 20 個・配信 5 本から。長さ = 中央値を 10〜120 秒に・山の前の割合は見本 10 個から)。
  理由: 10-05 の時点で友人の区間は 4 個・中央値 約 150 秒で、スタジオの既定 45 秒(ショート向け)の 3 倍以上 = 性質が違うので、ユーザー自身のまとめて実行・スタジオの解析には効かせない。
  目安は全体で 1 つの固定の長さ(場面ごとに長さを変えるには検出の仕組みの変更が要る。分布を見てから)
- 変わったふるまい: まとめて実行の中止で、その実行が入れたスタジオの解析も取り消す(今までは解析だけ動き続けた)

### 2-10. 送るアプリの画面の全面見直しで決まったこと(2026-10-02 ユーザー。ホーム 0.23.0・スタジオ 0.14.0・送るアプリ 2.0.0)
1. 配色は 4 つから選べる(A ネオンシアン(はじめの値)/ B シンセウェーブ / C ターミナルグリーン / D アイスライト)。窓の右上に切り替えを置き、選んだ配色は覚える
2. 前後の余白は 2 秒ずつ(PC が自動で付ける。友人には選ばせない)
3. 解析の重みは、音声・チャット・コメントの 3 つの数字を直接いじる(0.0〜3.0・0.1 刻み。はじめは 1.0・1.0・0.7 = スタジオの既定。「重みを指定する」を入れたときだけ出す)
4. 「時」は 1 桁で自動で次へ進む。10 時間より後は ↑ か URL の貼り付けで入れる、という説明を画面に出す
5. 時刻の欄は 1 つ。時 → 分 → 秒の順に左から数字だけで打つ(「:」は打たない。右から押し出す形は不採用)。←→ で場所を選ぶ。「+30秒」などのボタンは要る
6. 区間が切り抜く数に足りない分だけ自動で埋める。カットは「しない / 無音を削る」の 2 つ
7. 仕上げ方は毎回 ①。ほかの設定(カット・映像トラック・切り抜く数・重み・配色・窓の大きさ)は覚える。URL の題名を出す。届いた知らせは邪魔をしない形だけ(「受け取る ●n」・窓の題名の件数・タスクバーを数回光らせる。前に出さない・音なし・窓なし)
8. 同じ配信も受け付け、解析などは使い回す。③ + 時間指定はやらない
- 見た目の方向: サイバー風(暗い地・1px の線・ほぼ直角・見出しは等幅の番号つき・数字は等幅・アクセント 1 色 + 誤りの色 1 色)。飾りの光・ぼかしは使わない(WinForms で安く作れず読みにくい)。Windows 標準の灰色の部品を混ぜない
- やらないこと: 時刻のメモをまとめて貼る・区間に題名を付ける・アプリの中で動画を再生して位置を選ぶ(標準の部品では YouTube を再生できない)・明るい/暗いの切り替え・ホーム/スタジオ/編集の配色の変更

### 2-11. 将来に備える形: 字幕の「見た目」のまとまり(2026-10-05 ユーザー「字幕のフォントやパラメータなどを将来指定される場合がある」)
今は色だけを作った(2-8)。あとからフォント・大きさ・ふちなどを足しても形を変えずに済むよう、**色を単独の値で持たず「字幕の見た目」のまとまりの中の 1 項目にしてある**。
- **依頼の JSON**: `speakers` に人ごとのまとまり `"people": [{"name": "…", "style": {"color": "RRGGBB"}}]`(`names` は古い PC のために今までどおり書く)。あとで足すときは `style` に鍵を足すだけ(例: `font`・`size`・`outline`)。依頼全体の見た目(全員に共通)は、依頼の直下の `style` を予約する(今は書かない)
- **文書**: 話者に `sub = {"color": "#RRGGBB"}`(字幕の見た目。画面の行の色 `color` とは別の項目)。あとで `sub` に鍵を足す。**指定した色はその文書にだけ覚える**(PC の「自分の色」の一覧には登録しない = 友人の入力で PC の設定を恒久的に書き換えない)
- **cut2resolve の API とパック**: 色だけの `speakerColors` を増やさず、`output.speakerStyles = {話者の名前: {"color": …}}`。パックの中では `speaker_colors`(字幕ごとの文字の色 `fills`)へつなぐ。フォントなどを足すときは、同じまとまりから字幕ごとの値を作る(`speaker_outlines` と同じ道)
- **検査は鍵ごとの許可の一覧**(`intake.STYLE_KEYS`。知っている鍵だけ受け、型と長さを確かめ、知らない鍵は捨てる。`sanitize_pack_output` と同じ考え方)。色は外から来る文字なので受け取る側で必ず 16 進 6 桁だけに検査する(画面・Lua に入るため)。名前も長さと制御文字を検査(プルダウンでも打てる)
- 優先の順(あとで項目が増えても同じ): 人ごとの指定 → 依頼全体の指定 → メンバーカラーなど PC の決まり → PC の設定の既定
- 色だけ入れて名前が空の行は、送る前にアプリで止める。新しいアプリ + 古い PC / 古いアプリ + 新しい PC のどちらでも今までどおり動く(色のキーが無い・`streamer` だけ、を両方テスト)
- **フォントを足すときの注意(今は決めない)**: フォントは友人の PC ではなく、パックを開く Resolve の PC に入っているものしか使えない。名前を自由に打たせず、PC 側が持つ一覧から選ぶ形にする(今のパックも、指定のフォントが無いときの代わりを持っている)

### 2-12. 友人の受け取り側: すべて受け取る・展開・まとめ動画を見る・要らない(2026-10-07 ユーザー「一括受け取り機能を追加」「一日の上限を撤廃したい」「確認の時間を短縮させるアイデアが欲しい」。送るアプリ 2.3.0〜2.5.0・ホーム 0.44.0)
- **大前提(ユーザー)**: 友人の依頼では**判断はすべて友人が行う。送る側(ユーザーの PC)では確認しない**(無人で動いていることが多い)。
  見る・要らないと決める・Dropbox から消す はすべて友人のアプリ側に置き、PC 側は作って置くだけで人の操作を挟まない。
  線 D の M12「届けるのは人の確認のあと」はライブ録画の自動の切り抜き(ユーザー自身の案件)の話で、友人の依頼の ① には当てはめない
- 背景: 1 つの依頼から何本ものパック(1 本 数 GB)ができる。友人のアプリでは 1 本ずつ選んで「受け取る」→ zip を展開 → 確かめる の繰り返しで時間がかかり、PC 側の「1 日 5 件」で翌日に回されることもあった。
  確認の時間を短くする案 A〜E のうち、C(受け取ったら展開)= 2.4.0・B(依頼ごとにまとめ動画 1 本)= 2-13 で採用。A(プレビューで選んでから本番)は保留、D(字幕の文と点数を一覧に)・E(候補を見てからパックにする 2 段階)は却下
- **送るアプリの「受け取る」のタブ(2.5.0 の動き)**。依頼の JSON の形・鍵・設定ファイルは変えていない(2.2.0 までの PC とも今までどおり):
  - 一覧: Dropbox の `出力\` の zip と失敗の知らせ。zip と同じ名前の `.preview.mp4`(2-13 のまとめ動画)はそのパックに結びつけて一覧には出さない(相手のいない preview は出さず消しもしない = zip がまだ同期されていない間に消さないため)。
    一覧の下は「パック n 本・失敗の知らせ n 件があります」。パックを選ぶと「この依頼のパックは、届いている中に n 本」「まとめ動画: あり(18MB)」
  - **受け取る / すべて受け取る(n 本)**: 1 本ずつ、または届いているパックを**古い順**(できた順)にまとめて受け取る(失敗の知らせは含めない)。「すべて受け取る」は押すと本数と合計の大きさの確認を 1 回出す(数十 GB になり得るため)。
    1 本でも「すべて」でも同じ道筋 `Receiving.ReceiveOne`(受け取って大きさ・content_hash を確かめる → 展開 → Dropbox と一覧から消す)を通る。進み具合は全体のバイト数(「受け取っています(2 / 5 本目: 題)… (全体 2.5GB / 7.5GB)」)。
    そのファイルだけの問題(大きさが合わない・壊れていた・受け取っている間に作り直された)は飛ばして次へ進み、終わりに題を出す。通信・鍵・保存先の空きの問題は止める(次も同じ理由で失敗し、やり直しの待ちが積み上がるだけ)
  - **展開**(2.4.0): 受け取った zip は保存先に `<題>_pack` のフォルダとして展開し、zip は消す(1 本ずつでも「すべて受け取る」でも)。zip の中身が 1 つのフォルダならそれを保存先の直下に(同じ名前は「(2)」)、そうでなければ zip の名前のフォルダに。
    `<名前>.extracting` に書いてから名前を変え、途中で止まれば消して zip を残す。`..`・ドライブ名・使えない文字の名前は断る(zip は Dropbox 経由 = 鍵を知る人なら置けるため)。保存先の空きは zip + 中身の 2 倍で確かめる。
    展開できなかったとき(空き・壊れた zip)は zip を残して知らせ、Dropbox からは消す(受け取りは済んでいる)。`settings.json` の `"extractZip": false` で zip のまま(画面のスイッチは無い)
  - **やめる**: 1 本の受け取りでも押せる。途中のファイル(.part)は消す。受け取り終えて Dropbox から消す途中のものは消し終える(消すときだけ別のつながり = 「やめる」で止まらない。消さないと次の更新でまた出て二度受け取る)
  - **まとめ動画を見る**(2.5.0): preview を `%TEMP%\RequestSender\previews` に取ってきて既定のプレイヤーで開く(同じものが取ってあればそのまま)
    → **2.7.0(2026-10-08 ユーザー「届いたら自動でダウンロードしてアプリ上で再生」)**: 一覧を調べたとき(起動・更新・3 分ごとの確認)に preview を裏で 1 本ずつ先に取る(`src/Preview.cs` の `PreviewQueue`。一覧の順・押したものを先頭・300MB 超は押したときだけ・失敗は押したらもう一度・一覧から消えたものは取らない)。再生はアプリの小窓(`PreviewForm` = WPF の MediaElement を ElementHost で。.NET Framework 4 に同梱)で、[受け取る] [要らない] がそのまま続く。再生できない PC(N エディションなど)は「外部のプレイヤーで開く」、小窓が作れなければ既定のプレイヤーで開く
  - **要らない**(2.5.0): パックを受け取らずに Dropbox から消す(preview も)。失敗の知らせの「消す」と同じボタンで、選んだものにより文字を変える。
    2.6.0 からは消す前に「要らなかった」の記録を PC に戻す(2-14)。受け取った・要らないにしたパックのまとめ動画の写し(`%TEMP%` の中)は消す(受け取ったあとは要らない。2026-10-08 ユーザー)
- **ホーム(0.44.0)**: 依頼の受付の **「1 日の上限(件)」を撤廃**(`prefs` の `dailyMax`・`intake._room`・翌日に回す `held`)。設定の欄から外し、状態は「今日 n 件」(件数は数えるだけ)。
  古い prefs.json の `dailyMax` は読み飛ばす。配信の長さ(8 時間)・動画の大きさ(20GB)の上限は今までどおり(7)。鍵が漏れて大量に送られたときの備えは、Dropbox でアプリの接続を切ること(7 の 1 つ目)

### 2-13. PC の届け方: n 本ごとに 1 つの zip + まとめ動画(2026-10-07 ユーザー「n 本ごとに届けるに変更して(n=5 くらい)。まとめて動画を添えるのはあり。画質を落として・速くしてよい」「字幕はいらない / n=5 / 速度は 2 倍」。ホーム 0.45.0。**2026-10-08 ユーザー「左上の説明をずっと表示して等速で渡す」「受け取った後のプレビューはいらない」→ 等速・札はずっと・zip の中に まとめ.mp4 を入れない。ホーム 0.46.0**)
- **届け方(`autorun._deliver_pending` / `_deliver_batch`)**: ① 全自動のパックは**配信(= まとめて実行の 1 つの実行)ごとに n 本たまるごとに 1 つの zip**(`出力\<依頼 id>__<配信の題名> 1-5.zip`。中は `<題>_pack/` が並ぶ)。
  n はホームの設定 `intake.deliverBatch`(1〜10・既定 5。画面は「まとめて届ける本数」)。実行の終わり(止まったときも `_deliver_rest_quietly`)に n 本に満たない分が残っていればその本数で(7 本なら「1-5」「6-7」)。

- **まとめ動画(`deliver.make_preview`)**: n 本の切り抜き(各パックの中でいちばん大きい動画。`_roughcut` は除く)をつなげた 1 本。480p・crf 28・**等速**(`PREVIEW_SPEED` = 1。1 以外にすれば `setpts` + `atempo` で速くする。音の高さは変えない)・

  音の無いクリップが混ざれば音なし。5 本 × 90 秒で約 7.5 分・30〜50MB。ffmpeg の失敗・無しでは作らず、zip だけ届ける(届けるのは止めない)。速度・札・画質は `deliver.py` の定数(`PREVIEW_SPEED`・`PREVIEW_LABEL_SEC`・`PREVIEW_HEIGHT`・`PREVIEW_CRF`。設定の欄は作らない)
- **置き場所**: zip の**隣**に `<zip の名前>.preview.mp4`(友人のアプリが先にこれだけ取ってきて見る)。**zip の中には入れない**(0.46.0。受け取ったあとは要らない。0.45.x は `まとめ.mp4` を入れていた)。**preview を先に置き、zip をあとに置く**(zip が見えたらそろっている)。
  2.4.0 までのアプリは `.preview.mp4` を一覧に出さない(zip と .失敗.txt だけ)のでそのまま動く(受け取ると `<依頼 id>__<題名> 1-5\` のフォルダに n 本の `<題>_pack` が並ぶ)
- **届けた記録**: zip を置くたびに `logs\deliveries.jsonl` に 1 行(`autorun._record_delivery` → `friend_feedback.record_delivery`: zip の名前・依頼 id・実行 id・配信 id・パックのフォルダ・切り抜きの動画・マークの id)。2-14 の「要らない」が引く。書けなくても届けるのは止めない
- 友人のアプリから依頼ごとに n を指定する形は、要望が出てから(JSON に足すだけ)

## 3. 全体の流れ
```
友人の PC                          ユーザーの Dropbox(2TB)                  ユーザーの PC
依頼ボックス.exe ─API でアップロード→ /アプリ/切り抜き依頼/ ─同期→ Dropbox\アプリ\切り抜き依頼\
 (動画をドラッグ / URL を貼る)                                               │ ホーム(src/home/intake.py)が 30 秒ごとに見る
                                                                              ▼
                                                             検査 → まとめて実行(src/home/autorun.py)→ 文字起こし
                                                             元のファイルは 受付済み\日付\ へ(消さない)・断ったら 失敗\ へ + 理由
```
- PC から取りに行く形(ホームのポートを外に開けない)。1つの画面の XSS で全ツールの API が使える構造なので、外からの接続は受けない(AGENTS.md の【高】)
- 予備: ブラウザの Dropbox ファイルリクエスト(保存先を同じフォルダに)。友人のプログラムが動かないときに使う。容量は受け取る側(ユーザー)だけに数えられる

## 4. 友人のプログラム(依頼ボックス)

- 画面: 動画のドラッグの欄 / 配信の URL(複数可)と切り抜く数(1〜10)/ 配信者(任意。メンバーの一覧 `friend-apps/holo-colors/members.json` から選ぶ)/ メモ / 「送る」/ 進み具合と「送りました ✓」

- 送る前に確かめる(便利のため。本当の検査は PC 側): URL が YouTube か・動画の拡張子・数の範囲
- 送るもの: 動画があれば先に動画、**最後に依頼の JSON**(下の 5)。JSON が届いた = そろった、の合図にする(同期の途中のファイルを読まないため)
- Dropbox の API:
  - アプリは「App folder」の権限だけ(`/アプリ/切り抜き依頼/` の外は読めない・書けない)。スコープは `files.content.write` だけ(読みは要らない)

  - 名前がぶつかったら `autorename`。`Dropbox-API-Arg` のヘッダーの JSON は ASCII 以外を `\uXXXX` にする(日本語のファイル名で必要)

## 5. 依頼の形
### 5-1. 依頼の JSON(友人のプログラムが作る。`<日時>-<乱数>.request.json`)

## 6. PC 側(ホーム)

## 7. 安全
- 鍵(または予備のリンク)を知る人は誰でも依頼を入れられ、自動で流れる。対策:
  - 鍵はアプリ専用のフォルダだけ。漏れたら Dropbox の設定でアプリの接続を切れば無効(新しい鍵を渡し直す)
  - 上限で PC を長く占有させない(配信 8 時間まで・動画 1 本 20GB まで。設定で変えられる)。1 日の件数の上限(5 件)は 2026-10-07 に撤廃した(2-12。友人の依頼を翌日に回さない)
  - 送り主の名前・依頼の中身は本人の証明にならない。受け付けの判断には使わない
- 受け付ける URL は youtube.com / youtu.be の配信・動画だけ(11 文字の ID を取り出して、それだけを渡す。任意の URL を yt-dlp に渡さない)
- 他人が作った動画を ffmpeg で読むこと自体が攻撃の入口になり得る: 拡張子と ffprobe で形を確かめてから先へ。ffmpeg は新しく保つ
- JSON・テキストは大きさの上限(例 64KB)を付けて読み、知らないキーは捨てる。パスは見張るフォルダの中だけ(`..`・絶対パス・ネットワークのパスを断る。`fsio.is_network_path`)
- 見張るフォルダにネットワークドライブは選べない(段2 の「動画を選び直す」と同じ規則)
